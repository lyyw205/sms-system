### 🎯 목표 1 (최우선) — 관문 7개를 전부 fail-closed 로

> **폴더를 나누는 게 목적이 아닙니다. 우회하면 터지게 만드는 게 목적입니다.**

이 저장소에는 지켜야 할 **관문이 8개** 있습니다. 그중 **fail-closed(우회하면 예외)는 1개뿐**이고,
**그 1개만 우회가 0건**입니다. 나머지 6개는 전부 뚫려 있습니다.

| # | 관문 | 선언 안 하면 | 실제 우회 | 상태 |
|---|------|-------------|----------:|------|
| 1 | **테넌트 격리 (SELECT)** | **RuntimeError** ✅ | **0** | ⭐ **유일한 성공 — 이게 본보기** |
| 2 | 테넌트 격리 (벌크 삭제) | 전체 삭제됨 | **4 / 13** | [G-1·G-2](./01-정리대장.md) |
| 3 | 테넌트 격리 (INSERT) | `NULL` 로 저장 | 미측정 | [G-3·G-4](./01-정리대장.md) |
| 4 | **인가 (누가 뭘 하나)** | **로그인만으로 통과** | **52 / 104** | [G-6 → E-5](./01-정리대장.md) |
| 5 | 스키마 마이그레이션 | 운영에만 컬럼 없음 | **31컬럼** | [G-5](../db-schema-baseline.md) |
| 6 | 예약 필드 변경 (Mutator) | 그냥 대입됨 | **24곳** (08-31 재실측 약 15곳) | E-3 |
| 7 | 칩 생성 (chip_store) | 직접 생성됨 | 0 (우연) | E-2 |
| 8 | 방 배정 | **관문 자체가 없음** | — (4곳이 각자 방어) | E-1 |

**이건 우연이 아니라 법칙입니다.**

```
fail-closed 로 만든 관문  →  우회 0건
"이걸 쓰세요" 로 둔 관문  →  우회 4 · 24 · 31 · 52건

같은 저장소 · 같은 사람 · 다른 결과.
차이는 "우회하면 터지게 만들었나" 하나뿐입니다.
```

**측정 지표**: fail-closed 관문 **1/8 → 8/8** · 총 우회 **111건+ → 0** ※08-31 재실측: Mutator 우회 24→약 15 로 감소, 총 ~102건+ ([`07-계획갱신`](./07-계획갱신-2026-08-31.md) §0)

> ⚠️ **잠그기 전 제1원칙** — 우회에는 두 종류가 있고 처방이 정반대입니다.
>
> | 종류 | 원인 | 처방 |
> |---|---|---|
> | **(가) 안 지킴** | 지킬 수 있는데 관례라 무시 | ✅ 강제하면 해결 |
> | **(나) 못 지킴** | 관문이 그 기능을 안 담음 | 🔴 강제하면 **정당한 작업이 막힘** → **관문을 먼저 넓힘** |
>
> 실측 사례: `factory` 우회 9곳은 전부 **(나)** 였습니다 (아직 저장 안 한 쿠키 검증 · 언스테이블 제2계정).
> 그냥 잠갔다면 **네이버 쿠키 검증 기능이 통째로 막혔을 것**입니다. → P12.3 · [E-7](./01-정리대장.md)

## 1. 현재 구조 분석

### 1-1. 규모와 배치 (실측, 79파일 21,168줄 — 08-31 재실측 89파일 22,816줄, [`07`](./07-계획갱신-2026-08-31.md) §0)

이미 [`scripts/arch/check_layers.py`](../../../scripts/arch/check_layers.py) 에 목표 계층표가 들어 있고 검사기가 돕니다.
현재 배치를 계층별로 집계하면:

| 계층 | 파일 | 줄 | 비중 |
|------|-----:|----:|-----:|
| bootstrap | 4 | 937 | 4% |
| core (13개 하위) | 26 | 4,082 | 19% |
| module (10개) | 49 | 16,149 | **76%** |

**코어가 19%, 모듈이 76%.** 비율 자체는 건강합니다. 문제는 비율이 아니라 **선(edge)** 입니다.

### 1-2. 실측 — 지금 지울 수 있는 모듈은 10개 중 **2개**

| 모듈 | ←모듈 | ←코어 | →모듈 | 판정 |

| `party_ops` | 0 | 0 | 1 | ✅ **삭제 가능** |
| `reporting` | 0 | 0 | 1 | ✅ **삭제 가능** |

**해석이 명확합니다.**

- `party_ops`·`reporting` 이 지울 수 있는 이유는 잘 설계돼서가 아니라 **아무도 그들을 필요로 하지 않아서**입니다 (읽기 전용 말단).
- `custom_sends`(추가요금·파티MMS·업그레이드 2종)는 **26곳이 붙잡고 있습니다.** 설계상 가장 "플러그인"이어야 할 것이 가장 뽑기 어렵습니다.
- `custom_sends` 를 붙잡는 26건 중 **25건이 지연 import** 입니다. 즉 **이미 순환이 났고, 함수 안으로 숨겨서 덮어둔 상태**입니다.

### 1-3. 왜 이렇게 됐나 — 방향이 뒤집혀 있음

```
지금:   room_assignment ──▶ surcharge._delete_all_surcharge_chips  (배정 해제하니 추가요금 칩도 지워야 하네)
        naver_sync      ──▶ reconcile_surcharge_batch              (동기화했으니 추가요금도 다시 계산해야 하네)
        variables       ──▶ surcharge._is_double_room              (문자 변수 계산에 더블룸 판정이 필요하네)

문제:   "추가요금"이라는 기능을 뽑으려면 배정·동기화·문자변수를 전부 고쳐야 한다.
        = 추가요금은 모듈이 아니라 사실상 코어에 박혀 있다.
```

**호출 방향이 코어→모듈이 아니라 모듈→모듈이라서** 그렇습니다.
`custom_schedule_registry` 라는 레지스트리가 **이미 이 저장소에 있는데**, 칩 reconcile 경로만 레지스트리를 안 타고 직접 import 합니다.

## 2. 문제점

전수조사가 찾아낸 것을 **원인별로** 묶으면 4가지입니다.

### P1. 강제되지 않는 관문 — 이 저장소의 유일한 근본 원인

같은 코드베이스에서 결과가 갈렸고, 차이는 **딱 하나**입니다.

| 규칙 | 강제 방식 | 우회 |
|------|-----------|-----:|
| 테넌트 격리 | `before_flush`/`before_compile` + 컨텍스트 없으면 `RuntimeError` | **0건** ✅ |
| 예약 필드 변경 (Mutator) | docstring 약속 | **24곳** 🔴 |
| 칩 생성 (chip_store) | 약속 | 0건 (최근 정리) |
| 방 배정 | **관문 없음** | — (4곳이 각자 방어) |

→ **폴더를 나누는 것으로는 절대 안 됩니다.** 이 저장소가 이미 증명했습니다.

### P2. 같은 로직 두 벌 — 8건

어긋나면 **조용히** 다른 결과가 나옵니다. 상세는 [`02-무엇이-통합되나.md`](./02-무엇이-통합되나.md) §1.
가장 위험한 것: 파티 MMS 투숙 판정이 **SQL판·파이썬판** 두 벌 (어긋나면 칩이 샘).

### P3. 위치가 틀린 코어 — 13개 + 지연 import 239건

`stay_coverage_filter`("그날 우리 집에 있는 예약" — 6개 도메인이 씀)가 **스케줄링 모듈 안에** 갇혀 있습니다.
그래서 6개 도메인 중 10곳이 순환을 피하려 **함수 안에 import 를 숨깁니다.**

> **지연 import 239건은 문제가 아니라 증상입니다.** 계층 위반의 자백입니다.
> 코어일수록 숨은 호출이 많습니다 — `reconcile_all_chips` 17건, `stay_coverage_filter`·`today_kst` 각 10건.

## 4. Core 후보 — 확정

### 4-1. 코어의 정의를 바꿉니다

기존 정의("공통 기능 모음")로는 경계가 안 그어집니다. **데이터의 생애**로 정의합니다:

```
코어 = 예약 데이터가 태어나서 · 정제되고 · 관문을 지나 저장되고 · 파생 상태가 유지되는 파이프라인
```

이 정의의 실용적 효과: **"이 함수를 지우면 예약 데이터가 부정합해지는가?"** 로 판정이 됩니다.
`assign_room`(어느 방에 넣을지)은 지워도 데이터가 부정합해지지 않습니다 → 모듈.
`_reconcile_dates`(날짜 바뀌면 배정표 맞추기)는 지우면 부정합해집니다 → 코어.

### 4-2. 코어 확정 (계산 13개 + 승격 6개)

계산으로 나온 13개는 [`코어도출/요약.md`](./코어도출/요약.md) 에 있습니다. 이 설계가 **추가로 승격**하는 것:

| 승격 | 어디서 | 왜 |
|------|--------|-----|
| `send_single_sms` + 5겹 차단 | `sms_sender` (모듈) | **차단 5겹이 관문입니다.** 모듈에 두면 모듈 삭제 시 손님 오발송 방어가 같이 사라짐 |
| `_shift_daily_records`·`_reconcile_dates`·`unassign_room`·`clear_all_for_reservation`·`sync_sms_tags` | `room_assignment` (모듈) | I-1 조사 결과 = 배정 **유지**는 코어, **결정**만 모듈 |
| `product_capacity` (`_is_double_room`·`_is_dormitory_reservation`·`compute_guest_count`·`compute_excess`) | `surcharge` (모듈 private) | `variables.py` 가 private 4개를 직접 씀. 상품 정원은 도메인 어휘지 추가요금 소유가 아님 |
| `_to_response` (131줄) | `reservations_shared` | 예약 응답 직렬화 단일 소스 — **칩 표시 규칙이 여기 전부** 들어있음 |

| `ports` (`SMSProvider`·`ReservationProvider`) | `providers/base.py` | 아래 §4-3 |

### 4-3. 죽은 추상화 `providers/base.py` — **유지**하되 위치를 바꿉니다 (Q2/Q9 답)

정리대장은 "Mock 이 전부 삭제돼 구현체가 1개뿐 = 죽은 추상화"로 A-8 삭제 후보에 올렸습니다.
**재설계 관점에서는 반대 결론입니다.**

Protocol 을 지우면 코어가 `real/sms.py`(Aligo)·`real/reservation.py`(네이버)를 **직접 import** 해야 합니다.
= 코어가 외부 어댑터에 의존 = 계층이 무너지고, 테스트에서 실 API 를 끊을 수도 없습니다.

→ **결론: Protocol 은 코어의 포트(port)로 남깁니다.** 죽은 건 Protocol 이 아니라 `DEMO_MODE` 분기입니다.


## 5. Shared 후보 — 코어에서 분리해야 하는 것

**여기가 기존 설계에 없던 층입니다.** 지금은 전부 `core:*` 로 뭉뚱그려져 있습니다.

### 왜 나눠야 하나

사용자 목표는 "Core 는 절대 변경되지 않는다" 였습니다. 그런데 지금 `core:` 안에는 성격이 다른 둘이 섞여 있습니다:

```
업무 규칙이 바뀌면  →  바뀐다   (칩 계산 · 투숙 판정 · 라이프사이클)   ← 이건 Core
업무 규칙이 바뀌어도 →  안 바뀐다 (로깅 · 인증 · 세션 · 설정)          ← 이건 Shared
```

둘을 한 층에 두면 **도메인 규칙이 바뀔 때마다 "코어를 고쳤다"** 가 되어, "코어는 안정적"이라는 성질이 말로만 남습니다.

### Shared 확정 (11파일 · 2,024줄)

| 하위층 | 파일 | 역할 |
|--------|------|------|
| `shared/config` | `config.py` · `rate_limit.py` | 설정 · 레이트리밋 · `today_kst`/`KST` |
| `shared/storage` | `db/database.py` · `db/models.py` | 엔진 · 세션 · ORM 모델 |
| `shared/tenant` | `db/tenant_context.py` | **강제 관문 (본보기)** — 조회 우회 0건. ⚠️ 단 **벌크 삭제/수정에는 자동문이 안 걸림** → [G 그룹](./01-정리대장.md#g-관문-누수--이미-있는-관문에-뒷문이-있음) |
| `shared/auth` | `auth/utils.py` · `auth/schemas.py` · `auth/dependencies.py` · `api/deps.py` | 토큰 · 역할 · 테넌트 스코프 세션 |
| `shared/observability` | `diag_logger.py` · `activity_logger.py` · `event_bus.py` | diag 199종 · 감사로그 · SSE |
| `shared/api_contracts` | `api/shared_schemas.py` | `ActionResponse` (7줄인데 5개 모듈이 씀) |

### 의존 규칙 (3층)

```
        bootstrap          ← 전부 알아도 되는 유일한 곳
       ┌────┴────┐
       ▼         ▼
   modules/* ──▶ core/* ──▶ shared/*
       └──────────────────────▲       모듈은 shared 도 직접 씀 (로깅·인증)

   금지:  core  → modules      (R2)
          module→ module       (R3)   ★ 이게 삭제 가능성의 조건
          shared→ core         (R7)   ★ 신규
          shared→ modules      (R7)
```

> `shared` 는 **도메인 지식이 0** 이어야 합니다. `shared` 안에 "예약"·"칩"·"파티" 같은 단어가 나오면 잘못 배치된 것입니다.
> (예외: `db/models.py` 는 스키마라 도메인 명사가 나옵니다. 스키마는 저장 계약이지 판단 로직이 아니므로 shared 로 둡니다.)

### 6-2. 모듈 간 협력을 어떻게 없애나 — 이 설계의 핵심

남는 진짜 문제는 **"한 모듈의 작업이 다른 모듈의 후처리를 유발"** 하는 19건입니다.

이전 설계안은 `modules/X/public.py` (공개 계약)를 후보로 뒀는데, **그건 목표를 달성하지 못합니다.**
A 가 B 의 `public.py` 를 import 하면 여전히 inbound edge 이고, **B 를 지우면 A 가 깨집니다.**

→ **모든 모듈 간 협력은 코어의 레지스트리를 경유합니다.** 두 종류뿐입니다:

#### (가) 순서 있는 훅 — 후처리형 (비동기적 협력)

```python
# core/lifecycle/hooks.py  — 코어가 지점과 순서를 선언
HOOK_POINTS = {
    "reservation.synced": ["stay_group", "room_assign", "chip", "event_sms"],  # ★ 순서 고정
    "reservation.dates_changed": ["daily_records", "assignment", "chip"],
}
def emit(point, ctx): ...   # 등록된 슬롯만 선언 순서대로 실행

# modules/stay_group/registration.py — 모듈이 자기를 꽂음
hooks.register("reservation.synced", "stay_group", detect_and_link_consecutive_stays)
```

> ⚠️ **순서 없는 발행/구독으로 만들면 반드시 깨집니다.**
> 조사 F1-1 이 증명했습니다: `Phase 4 연박감지 → 4b 침대정렬 → 5 자동배정 → 칩 정합` 은
> **진짜 데이터 의존**입니다. 칩 정합이 자동배정보다 앞서면 건물 조건 칩이 안 생겨 연산이 2배가 되고 칩이 샙니다.
> 그래서 이벤트 버스가 아니라 **순서를 코어가 선언하는 훅 레지스트리**여야 합니다.
>
> 덤: `diff_trace.py` 가 diag 이벤트 **순서까지** 검사하므로(조사 R6-1), 이 순서 계약은 **자동으로 지켜집니다.**

#### (나) 능력 포트 — 동기 협력 (결과를 즉시 써야 함)

`extend_stay`(stay_group)가 `assign_room`(room_assign)을 부르고 **결과를 응답에 담아야** 하는 경우입니다.
훅으로는 불가능합니다.

```python
# core/ports/room_allocator.py
class RoomAllocator(Protocol):
    def assign(self, db, reservation_id, room_id, dates) -> AssignResult: ...

def get() -> RoomAllocator | None: ...   # 미등록이면 None
```

호출부는 `if (alloc := room_allocator.get()) is None: → "배정 기능 없음"` 을 명시적으로 처리합니다.
**모듈을 지우면 포트가 비고, 호출부는 정의된 축소 동작을 합니다.** 깨지지 않습니다.

| 협력 | 방식 |
|------|------|
| naver_sync → 연박/분할/자동배정/이벤트문자 (13건) | (가) 순서 훅 |
| reservations API → stay_group 후처리 (7건) | (가) 순서 훅 |
| reservations_stay → assign_room / unassign_dates (3건) | (나) 포트 |
| event_sms_hook → TemplateScheduleExecutor (1건) | (나) 포트 |
| custom_sends reconciler 25건 | **레지스트리** (이미 있는 패턴 확장) |
| `stay_coverage_filter`·`send_single_sms`·`product_capacity` | **코어 승격** (협력이 아니라 오배치) |

## 8. 리팩토링 전략

### 8-1. 이식 방식 — (나) 병행이 아니라 **(가) 점진 + shim**

방법론 문서는 (나) 병행 재작성을 권했습니다. **재설계 후 판단은 (가) 점진입니다.** 이유:

| | (나) 병행 재작성 | **(가) 점진 + re-export shim** |
|---|---|---|
| 되돌리기 | 스위치 시점에만 | **매 커밋마다** |
| 황금 비교 | 구/신 동시 실행 필요 (운영 DB 스냅샷 하네스 신규 구축) | **불필요** — 이동은 no-op 이므로 기존 diag-golden 이 그대로 안전망 |
| 안전망 | 새로 만들어야 함 | **이미 있음** (테스트 63파일 + 검사기 baseline) — ⚠️ 단 diag-golden 은 실측 23% |
| 위험 | 스위치 순간에 집중 | 분산 |

이 저장소는 **이미 안전망이 돌고 있습니다.** 병행 재작성은 그 안전망을 못 쓰고 새 하네스를 지어야 합니다.

> 🔴 **08-31 재실측 — 이 전제가 깨져 있었습니다.** 테스트 18건(수집 오류 2 + 실패 16)이 3.5개월 방치됐고 CI 가 실패를 삼키는 중이었음. 전략((가) 점진)은 유지하되 **P0.6 안전망 수복**을 선행 조건으로 신설 (Q38) → [`07-계획갱신-2026-08-31.md`](./07-계획갱신-2026-08-31.md) §3

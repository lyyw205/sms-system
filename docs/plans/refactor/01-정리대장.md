# E. 관문 강제 — 보호가 흩어져 있음

> "여러 함수가 **각자** 그 데이터를 지키고 있다" = 한 관문으로 모아야 한다는 신호.

## ⚠️ E단계 제1원칙 — 잠그기 전에 **관문이 충분한지** 먼저 확인 (Q23)

우회에는 **두 종류**가 있고, 처방이 정반대입니다.

| 종류 | 원인 | 처방 | 실측 사례 |
|------|------|------|-----------|
| **(가) 안 지킴** | 지킬 수 있는데 관례라서 무시 | ✅ **강제하면 해결** | Mutator 24곳 · G-1 4곳 · G-6 52곳 |
| **(나) 못 지킴** | 관문이 그 기능을 **안 담고 있음** | 🔴 **강제하면 정당한 작업이 막힘** | [E-7](#e-7) factory 우회 9곳 |

```
(나) 를 (가) 로 착각하고 잠그면:

관문 강제  →  정당한 작업이 막힘  →  급하니까 우회 구멍을 다시 뚫음  →  💥 원점
```

**→ E-1~E-6 을 잠그기 전에, 각 관문마다 "지금 우회하는 곳이 왜 우회하는지" 를 먼저 분류해야 합니다.**
(나)로 판정된 것은 **관문을 넓히는 게 먼저**입니다.

> 이 원칙은 ⑥ `core/ports` 단위 리뷰에서 발견됐습니다. factory 를 그냥 잠갔다면
> **네이버 쿠키 검증 기능이 통째로 막혔을 것**입니다.

| # | 데이터 | 각자 지키는 함수 수 | 현재 관문 | 제안 |
|---|--------|-------------------:|-----------|------|
| E-1 | **방 배정** (`RoomAssignment.reservation_id/date/room_id`) | **4** | **없음** 🔴 | 관문 신설 |
| E-2 | 문자 칩 (`reservation_id` 8 · `template_key`/`sent_at`/`date` 6 · `send_status` 5) | **8** | `chip_store` (약속) | **강제로 승격** |
| E-3 | 예약 필드 (`Reservation.id` 9 · `stay_group_id` 3 · `tenant_id` 3) | **9** | `Mutator` (약속, 우회 24곳 — 08-31 재실측 약 15곳, [`07`](./07-계획갱신-2026-08-31.md) §0) | **강제로 승격** |
| E-4 | 테넌트 (`tenant_id` 전반) | — | **이미 강제** ✅ | 유지 — 이게 본보기 |
| <a id="e-5"></a>**E-5** ⭐ | **인가(누가 뭘 할 수 있나)** | 엔드포인트 104곳이 각자 | **선언 안 하면 통과** 🔴 | **관문 신설 + 기동 시 fail-closed** ([G-6](#g-6--cleancrew청소-담당가-예약-삭제문자-발송-가능) 의 해결 수단) |

### E-7 factory 관문 확장 — **잠그는 게 아니라 넓히는 것**

`factory` 는 정상 사용 9곳 · 우회 9곳입니다. **우회 사유를 확인하니 전부 정당했습니다.**

| 사유 | 곳 | 왜 factory 로는 못 하나 |
|------|---:|------------------------|
| **아직 저장 안 한 쿠키 검증** | 5 (`api/settings.py`) | 관리자가 **방금 입력한** 쿠키가 유효한지 실제 호출로 확인해야 함. factory 는 **DB에 저장된** 쿠키만 읽음 |
| **언스테이블 계정** | 2 (`jobs.py` · `reservations.py`) | 한 펜션이 네이버 계정을 **2개**(`naver_*` / `unstable_*`) 씀. factory 는 스테이블만 앎 |
| 기타 | 2 | 확인 필요 |

**→ 해결은 강제가 아니라 시그니처 확장:**

```python
get_reservation_provider(business_id, cookie)                              # 기본형 — 임의 자격증명
get_reservation_provider_for_tenant(tenant, account="stable"|"unstable")   # 편의형
```

넓힌 **다음에** 잠그면 우회 9곳이 자연히 0이 됩니다. 순서를 바꾸면 기능이 막힙니다.

### E-6 `DEMO_MODE` — 이름 변경 + 기본값 뒤집기

**원래 목적은 이미 죽었습니다** — "실제 문자를 안 보내는 안전장치"였는데 Mock 구현체가 전부 삭제돼 Mock/Real 전환 코드가 한 줄도 없습니다.

**그런데 그 스위치에 나중에 6개가 물렸습니다:**

```
       ┌── ❌ Mock 문자 발송           ← 원래 목적. 이미 떼어냄
       │
       ├── ✅ JWT 시크릿 자동생성 vs 필수      (없으면 기동 거부)
       ├── ✅ Admin/Staff 비밀번호 자동생성 vs 필수
DEMO_  ├── ✅ CORS `*` 허용 vs 금지            (금지 위반 시 기동 거부)
MODE ──┤
       ├── ✅ Sentry 초기화 조건
       ├── ✅ Swagger UI 노출 조건
       └── ✅ health check 에러 상세 노출
```

→ **그냥 지우면 프로덕션 안전장치 6개가 같이 사라집니다.** "삭제"가 아니라 "정리"입니다.

**🔴 지금 문제 — 기본값이 안전한 쪽이 아닙니다:**

```python
DEMO_MODE: bool = True     # 기본값 = 데모 = 안전장치 꺼짐
```

`.env` 에 `DEMO_MODE=false` 를 **깜빡하면 조용히** 이렇게 됩니다:

| 결과 | 영향 |
|------|------|
| JWT 시크릿이 매 기동마다 랜덤 생성 | **재시작할 때마다 전원 강제 로그아웃** |
| CORS `*` | 아무 도메인에서나 API 호출 가능 |
| Swagger 노출 | API 구조 공개 |

**터지지 않고 조용히 약해집니다** — G 그룹 전체와 같은 형태입니다.

| | |
|---|---|
| 조치 | ① Mock 잔재(문서·이름) 정리 ② **이름 변경** (`DEMO_MODE` → 의미에 맞게, 예: `DEV_MODE`) ③ **기본값 뒤집기** — 안전한 쪽이 기본 |
| 효과 | 설정을 깜빡해도 **안전한 상태로 뜸.** 편의를 원할 때만 명시적으로 켬 |

@event.listens_for(Session, "before_flush")
def _reject_ungated_writes(session, ctx, instances):
    if session.info.get('mutator_active'):
        return                      # 관문 통과 중 → OK
    for obj in session.dirty:
        if isinstance(obj, Reservation) and _changed(obj) & GUARDED:
            raise RuntimeError("Mutator 없이 예약 필드를 바꿀 수 없습니다")

# G. 기반 누수 — 자동이어야 할 것을 손으로 지키다 빠뜨림

> 발견 2026-08-06 (`shared/tenant`·`shared/storage` 단위 리뷰 중) · **A~F 어디에도 없던 신규 유형**
> 성격이 다릅니다: A~F 는 "구조가 지저분하다"이고, **G 는 "기반이 이미 새고 있다"** 입니다.
>
> **G 를 하나로 묶는 병**:
>
> ```
> 자동으로 지켜져야 할 기반 장치가       →  손으로 유지되고 있고        →  이미 빠뜨렸다
> ─────────────────────────────       ────────────────────       ──────────────
> G-1~4  테넌트 격리(벌크 삭제 구간)        13곳에 손으로 필터            4곳 누락
> G-5    스키마 마이그레이션                57개 ALTER 를 손으로 작성      31컬럼 누락
> ```
>
> A~F 를 아무리 잘 정리해도 이 병은 안 낫습니다. **강제 장치를 다는 것만이 해결책**입니다.

## 배경 — 자동문이 닿지 않는 구간

테넌트 격리는 이 저장소에서 **유일하게 강제되는 관문**이고 조회 우회는 0건입니다.
그런데 자동 필터(`Query.before_compile`)는 **일반 SELECT 에만** 걸립니다.
`.delete()` / `.update()` 같은 **벌크 연산에는 발동하지 않습니다** (SQLAlchemy 2.0 사양 — 별도 이벤트 `before_compile_delete`/`_update` 가 존재하는 이유).

**개발자는 이미 알고 있었습니다.** 벌크 삭제 지점마다 손으로 막고 `(현재 테넌트만)` 주석을 달아뒀습니다.
문제는 **손으로 막는 방식이라 빠뜨렸다**는 것입니다.

```
테넌트 격리 = 이 저장소에서 유일하게 성공한 관문 (조회 우회 0건)
```

## ✅ I-1 — `room_assignment` 분리선 검증

| 검사 | 결과 |
|------|------|
| 공유 모듈 상태 | **없음** (`logger` 뿐) |
| 모듈 → 코어 호출 | 정상 방향 (`assign_room` → `_compact_bed_orders_in_cells`, `sync_sms_tags`) |
| 코어 → 모듈 호출 | **1건만** — `_reconcile_dates` → `_compute_bed_order` |

**결론: 분리 가능.** 다만 걸린 1건은 **분리선을 잘못 그은 것**이었습니다.
침대번호 계산·비밀번호 재사용·번호 정리는 "어느 방에 넣을지 결정"이 아니라
**"배정 레코드를 정합하게 유지"** 쪽입니다.

**정정된 분리선 — 결정 vs 유지:**

```
코어 (유지)   날짜 이동 · 범위 정합 · 침대번호 계산/정리 · 비번 재사용 · 해제 · 칩 동기화
모듈 (결정)   충돌 검사 · 도미토리 성별/정원 밀어내기 · 자동배정 알고리즘
```

이렇게 그으면 **코어 → 모듈 호출이 0** 이 됩니다.
⚠️ 단 `assign_room`(358줄) 자체가 결정+유지를 섞고 있어 **이 함수도 쪼개야** 합니다.

## ✅ F1-1 — `naver_sync` Phase 순서 의존성

```
Phase 4   연박 감지       → stay_group_id 생성
Phase 4b  침대번호 정렬   → 4의 결과(연결된 그룹)에 의존
Phase 5   자동 배정       → stay_group_id 로 "같은 방 유지" 판단    ← 4에 의존
Phase 5후 칩 정합         → RoomAssignment 필요 (건물 필터 통과)     ← 5에 의존
Phase 6   이벤트 문자     → 신규 id 만 필요                         ← 독립
```

**결론: 4 → 4b → 5 → 칩 은 진짜 데이터 의존.** 이벤트 문자만 독립.

→ 이벤트 버스로 바꾸려면 **실행 순서를 명시적으로 선언**해야 합니다.
순서 없는 발행/구독으로 만들면 깨집니다.

# 전면 리팩토링 — 방법론

> 작성 2026-08-06 · 상태: **방법 확정 대기**
> 이전 시도(`docs/plans/_archive/architecture-refactor-*.md`)는 **폴더 배치 중심**이라 폐기. 실측 수치만 참고.

---

## 0. 목표

> "모든 기능·예외·변수를 전수조사해 리스트업하고, **그 동작을 100% 유지한 채** 코어층을 확실히 잡고 도메인에 맞게 하나씩 끼워 넣는다."

핵심은 두 가지다:

1. **동작 보존이 최우선** — 기능이 하나라도 바뀌면 실패. 리팩토링은 "동작 같음 + 구조 다름"이다.
2. **코어는 강제되어야 한다** — 폴더로 나누는 게 아니라, **우회하면 터지게** 만든다.

---

## 1. 왜 "폴더 나누기"로는 안 되는가

| 수단 | 강제력 | 근거 |
|------|--------|------|
| 폴더 배치 | **0** | import 는 폴더를 넘어간다 |
| 네이밍 규칙 (`_private`) | 낮음 | `_delete_all_surcharge_chips` 가 3개 모듈에서 호출 중 |
| import 검사기 | 중간 | CI 에서만 작동, 런타임 우회 못 막음 |
| **런타임 관문 (fail-closed)** | **높음** | 우회 시 예외 |

**이 저장소에 이미 증거가 있다.**

| 관문 | 강제 방식 | 우회 건수 |
|------|-----------|-----------|
| **테넌트 격리** | `before_flush` / `before_compile` 이벤트 + 컨텍스트 없으면 `RuntimeError` | **0** ✅ |
| **chip_store** (칩 생성) | 관례 (강제 없음) — 다만 최근 통합 완료 | 0 ✅ |
| **ReservationMutator** | 관례만 (docstring 약속) | **24** 🔴 |

같은 코드베이스, 같은 개발자, 다른 결과. 차이는 **강제 여부** 하나다.

→ **결론**: 코어의 정의는 "core/ 폴더에 있는 것"이 아니라 **"우회할 수 없는 관문을 가진 것"** 이다.

---

## 2. 코어의 정의 — 데이터의 생애

코어를 "공통 기능 모음"이 아니라 **예약 데이터가 태어나서 저장되고 파생 상태를 유지하는 파이프라인**으로 정의한다.

```
┌──────────────────────── 코 어 ────────────────────────┐
│                                                        │
│  ① 인입        ② 정제         ③ 관문        ④ 저장    │
│  ──────       ──────         ──────       ──────      │
│  네이버 API    ''→None        Mutator       DB         │
│  언스 API      날짜 정규화     권한행렬                  │
│  수기 입력     성별 파싱       pin 보호                  │
│                party 상속     ⚠ 우회 시 예외            │
│                                                        │
│  ⑤ 파생 상태 유지                                       │
│  ─────────────                                         │
│  칩 reconcile · 일자별 배정레코드 · 연박/분할 그룹        │
└────────────────────────────────────────────────────────┘
                        ↓ 읽기 + 관문 경유 쓰기
   ┌─────────┬─────────┬─────────┬─────────┬─────────┐
   │ 방 배정  │ SMS 발송 │ 스케줄링 │ 파티 운영 │ 리포팅   │  ← 모듈
   └─────────┴─────────┴─────────┴─────────┴─────────┘
     · 서로를 모른다
     · 하나가 죽어도 나머지는 정상 동작
     · 새 모듈 추가 시 기존 모듈 코드 변경 0
```

이 정의에 따르면 현재 `naver_sync.py`(1,008줄)는 **코어와 모듈이 섞인 파일**이다:

| 함수 | 성격 |
|------|------|
| `_parse_gender_from_custom_form` · `_parse_datetime` · `_init_gender_counts` | ② 정제 → **코어** |
| `_create_reservation` · `_update_reservation`(265줄) | ④ 저장 → **코어** |
| `_split_multi_room_reservations` · `_align_bed_orders_for_groups` | ⑤ 파생 → **코어** |
| `sync_naver_to_db`(420줄) — 방배정·연박·이벤트SMS 호출 | 오케스트레이션 → **모듈 호출부** |

## 3. 전수조사 — 무엇을 어떻게 세는가

"전수"라고 부르려면 **빠진 게 없음을 증명**할 수 있어야 한다. 각 층마다 기계적 전수 방법이 있다.

| 층 | 대상 | 전수 방법 | 실측 |
|----|------|-----------|------|
| **L1** | 진입점 | 라우터 데코레이터 · `add_job` · `event.listens_for` AST 추출 | **104 API + 12 잡 + 2 DB이벤트 + 1 SSE** |
| **L2** | 기능(행위) | L1 에서 도달 가능한 호출 그래프 | 438 함수 |
| **L3** | 분기·예외 | `ast.If` / `Try` / `IfExp` 전수 | **1,551** |
| **L4** | 변수·도메인값 | DB 컬럼 + enum-like 리터럴 + Settings + 템플릿 변수 | 24 모델 · 축 20+ |
| **L5** | 불변식 | `diag-golden/invariants.md` + 특성화 테스트 | INV-1~8 · diag 199종 |

### L3 이 관건 — 1,551개를 어떻게 다루나

전부를 문장으로 적을 수는 없다. **분류해서 취급을 달리한다.**

| 등급 | 의미 | 처리 | 예시 |
|------|------|------|------|
| **D** 도메인 규칙 | 비즈니스 판단 | **개별 명세 필수.** ID 부여, 재조립 시 체크 | `not co or co == ci` (당일 1박) |
| **G** 가드/보호 | pin · 권한 · 무결성 | **개별 명세 필수** | `if check_out_pinned: skip` |
| **L** 레거시 호환 | 구버전 데이터 수용 | 명세 + 폐기 가능성 판단 | filters v1/v2 dual-parse |
| **N** 존재 확인 | null/404 체크 | 구조적 처리 (개별 명세 불필요) | `if not res: raise 404` |
| **I** 인프라 | 트랜잭션·재시도·로깅 | 구조적 처리 | `try/except: rollback` |

**D + G 만 개별 보존 대상**이다. 이걸 추려내는 게 조사의 본체다.

> ⚠️ 분류는 **기계가 초안, 사람이 확정**한다. 자동 분류를 그대로 믿으면 도메인 규칙을 N 으로 오분류해 잃는다.

## 4. 산출물 — 명세 카드

D/G 항목마다 카드 하나. 이게 "하나씩 끼우는" 단위다.

```yaml
id: D-STAY-001
층: 코어 / calendar
규칙: check_out_date 가 NULL·''·check_in_date 와 같으면 "당일 1박"
현재위치: services/stay_logic.py:12, schedule_utils.py:25, template_scheduler.py:844
목표위치: core/calendar/stay.py
예외:
  - '' 은 Python truthy 로는 NULL 과 같으나 SQL is_(None) 에서 갈라짐
  - co < ci 는 중화되어 [ci] 1박 (LB-03 잠재버그, 현행 보존)
근거: docs/plans/stay-semantics-design.md §1
검증: tests/unit/test_stay_logic.py (특성화 15케이스)
상태: 조사완료 / 명세작성 / 이식완료 / 검증완료
```

카드가 전부 `검증완료` 가 되면 리팩토링이 끝난 것이다. **체크리스트가 곧 완료 조건**이다.

## 5. 이식 방식 — 세 가지 중 선택

| 방식 | 내용 | 위험 | 검증 난이도 |
|------|------|------|-------------|
| **(가) 점진 이동** | 기존 파일을 조금씩 옮기고 고침 | 낮음 | 낮음 (매 단계 diff) |
| **(나) 병행 재작성** | 새 코어를 옆에 새로 짓고, 준비되면 스위치 | 중간 | **중간** (구/신 동시 비교 가능) |
| **(다) 전면 재작성** | 처음부터 다시 씀 | **높음** | 높음 (한 번에 전부 검증) |

말씀하신 *"코드를 처음부터 다시 작성하더라도"* 는 (나) 또는 (다) 인데, **(나) 병행 재작성**을 권한다:

- 새 코어를 `app/core2/` 같은 곳에 짓고 기존 코드는 손대지 않는다
- **황금 비교(golden diff)**: 같은 입력을 구/신 양쪽에 넣어 출력이 같은지 자동 대조
- 카드가 전부 통과하면 스위치, 아니면 언제든 되돌림
- (다) 와 달리 **되돌아갈 곳이 항상 있다**

## 6. 동작 보존 증명 — 3중 안전망

| 망 | 도구 | 잡는 것 |
|----|------|---------|
| 1. **특성화 테스트** | `tests/` (현 67파일 10.8k LOC) + 신규 | 함수 단위 입출력 |
| 2. **diag-golden** | `docs/diag-golden/` (199 이벤트, 정답지 YAML) | 실행 경로·순서 |
| 3. **황금 비교** | 신규 — 운영 DB 스냅샷에 구/신 동시 실행 후 출력 대조 | 통합 동작 |

⚠️ **diag 이벤트 문자열은 동결**한다. 이게 깨지면 정답지 전체가 무효가 되어 안전망 2가 사라진다.

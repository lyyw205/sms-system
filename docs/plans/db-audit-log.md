## 2. 설계 — 두 축으로 나눕니다

> ⚠️ **감사 로그는 diag 를 "대체"하지 않습니다. 각자 다른 것을 봅니다.**

```
┌─ 축 1. 감사 로그 (신규) ────────────────────────────────┐
│  질문: "무엇이 바뀌었나"                                  │
│  방식: ORM 이벤트로 자동 포착 — 빠뜨릴 수 없음             │
│  용도: "이 예약 체크아웃이 왜 바뀌었지?" → 범인 추적        │
└──────────────────────────────────────────────────────────┘

┌─ 축 2. diag (축소 · 재배치) ────────────────────────────┐
│  질문: "왜 안 일어났나"                                   │
│  방식: 손으로 심되 **결정 지점에만**                       │
│  용도: "왜 문자가 안 나갔지?" → 차단·제외·skip 사유        │
└──────────────────────────────────────────────────────────┘
```

### 🔴 왜 diag 를 전부 없애면 안 되는가

감사 로그는 **"일어난 일"만** 봅니다. 그런데 이 시스템에서 가장 자주 묻는 질문은
**"왜 안 일어났지?"** 이고, 그건 **DB 변경이 0이라 감사 로그에 한 줄도 안 남습니다.**

```
스케줄 필터에서 제외됨            → 대상 목록에서 빠짐.   DB 변경 0
업그레이드 "노리는 밤 아님" skip   → 칩 안 만듦.          DB 변경 0
reconcile 이 "변경 없음"으로 종료  →                     DB 변경 0
미치환 변수 차단 (F-3)            → 발송 안 함 + 기록도 안 남김. DB 변경 0
```

이 시스템 로직의 절반이 이런 판단입니다.

### 포착 대상

```python
@event.listens_for(Session, "before_flush")
def _audit(session, flush_context, instances):
    for obj in session.new:      # INSERT
    for obj in session.dirty:    # UPDATE — attributes.get_history() 로 before/after
    for obj in session.deleted:  # DELETE
```

부가 정보: `req_id`(이미 있음) · `user` · `tenant_id` · 타임스탬프 · 호출 경로

## 3. 🔴 선행 조건 — G-4 (벌크 연산 이벤트)

**ORM `before_flush` 는 벌크 연산을 안 탑니다.**

```
db.add() · obj.field = X · db.delete(obj)   →  포착됨   ✅
query.delete() · query.update()             →  안 잡힘  🔴
```

이 저장소는 벌크 삭제/수정을 **13곳**에서 씁니다 — 칩 삭제·배정 해제 등
**가장 중요한 변경이 통째로 안 잡힙니다.**

→ **[G-4](./refactor/01-정리대장.md) (`before_compile_delete` / `before_compile_update` 추가)
가 이 프로젝트의 선행 조건입니다.** 마침 G-1·G-2(테넌트 필터 누락)의 근본 해결과 같은 작업입니다.

```
G-4 (벌크 연산 이벤트 신설)
  ├─ 효과 A: 테넌트 필터 자동 적용    → G-1·G-2 구조적 재발 방지
  └─ 효과 B: 벌크 변경 감사 포착      → 이 프로젝트의 전제
```

### V1 볼륨이 왜 중요한가

네이버 동기화가 **5분마다** 돌며 예약 수백 건을 훑습니다. 모든 UPDATE 를 남기면 하루 수만 줄이 될 수 있습니다.

> 이 저장소는 이미 볼륨 감각이 있습니다 — **"시간대 제거(변환 아님)"** 방어의 이유가
> *"확정 예약마다 5분마다 쓸데없는 업데이트"* 였습니다.

| 저장 위치 | 장점 | 단점 |
|---|---|---|
| 파일 (현 diag 방식) | 부하 작음 · grep 추적 | 화면 연동 불가 · 보존 관리 |
| DB 테이블 | 조회·화면 연동 · SQL 질의 | 쓰기 2배 · 테이블 비대 · 테넌트 격리 대상 |
| 하이브리드 | 전체는 파일 · 중요 변경만 DB | 두 곳 관리 |

### A5 diag 재배치가 이 프로젝트의 본체입니다

199종을 3분류합니다:

| 분류 | 처리 | 예 |
|------|------|-----|
| **"일어난 일"** (생성·삭제·변경) | 🗑 **제거** — 감사 로그가 자동으로 덮음 | `chip_store.*.created` `assign_room.exit` |
| **"안 일어난 일"** (차단·제외·skip) | ✅ **유지** — 감사 로그가 못 봄 | `sms_sender.blocked_*` `*.skipped` `filter.*` |
| **"심어야 하는데 없는 곳"** | ➕ **신규 추가** | 리팩토링 중 발견한 무계측 분기 |

> **예상**: 199종 → 40~60종으로 축소 (실측 필요)
>

> "여기 로그가 있어야 하는데 없네" 를 같이 수집합니다. 리팩토링이 코드를 전부 훑는
> 유일한 기회이므로, **그때 같이 표시해두지 않으면 다시 전수조사를 해야 합니다.**

## 6. 리팩토링과의 관계

### 왜 리팩토링 "후"인가 (Q15)

리팩토링을 진행하면서 **"diag 를 새로 심을 곳"까지 함께 식별**하기 위함입니다.
코드를 전부 훑는 유일한 기회를 활용합니다.

### ⚠️ 그 결과 — 리팩토링의 no-op 증명 수단이 다시 열립니다

원래는 "감사 로그를 먼저 만들어 **DB 변경 집합 비교**로 no-op 을 증명한다"가 가능했습니다.
후행으로 정하면 그 카드가 없어지므로, 리팩토링은 **기존 안전망**으로 증명해야 합니다.

| 안전망 | 실측 | 판정 |
|---|---|---|
| ① 특성화 테스트 | 63파일 10,786줄 · **서비스층 두터움** | ✅ 주력 |
| | 🟡 API 층은 4파일 (엔드포인트 104개) | 얇음 |
| ② diag-golden | **47/199 (23%)** · 고위험 4모듈 0% | 🔴 약함 |
| ③ 황금 비교 | 없음 | — |

**→ `refactor/03-아키텍처-재설계.md` 의 P0.7 을 "정답지 보강"이 아니라
"특성화 테스트 보강"으로 바꿉니다.** (Q16)

이유: 정답지 체계는 이 프로젝트에서 **은퇴 예정**입니다. 은퇴할 체계에 새 정답지를
쓰는 것은 버리는 일이 됩니다. 테스트는 리팩토링 후에도, diag 은퇴 후에도 남습니다.

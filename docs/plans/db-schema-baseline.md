### 마이그레이션이 3중화돼 있습니다

앱이 기동할 때 **세 장치가 순서대로 전부 돕니다**:

```
컨테이너 기동
    │
    ├─① backend/entrypoint.sh:5      alembic upgrade head        (버전 관리 마이그레이션 35개)

    └─② gunicorn → app/main.py:177   init_db()
```

## 2. 왜 이게 위험한가 — 핵심 메커니즘

`Base.metadata.create_all()` 은 **없는 테이블은 만들지만, 있는 테이블에 컬럼은 못 넣습니다.**

```
새 테이블 추가  →  create_all 이 만들어줌      →  로컬 ✅   운영 ✅
새 컬럼 추가    →  create_all 은 아무것도 안 함 →  로컬 ✅   운영 ❌
```

```
로컬 개발자                        운영 서버
DB를 지우고 다시 만듦               DB가 계속 살아 있음
      ↓                                 ↓
create_all 이 전부 새로 만듦        테이블이 이미 있어 create_all 이 건너뜀
      ↓                                 ↓
새 컬럼 있음 ✅                     새 컬럼 없음 ❌
      ↓                                 ↓
테스트 통과 → 배포                  그 컬럼을 건드리는 순간 500
```

**그래서 컬럼 추가는 alembic 이나 `init_db` ALTER 에 손으로 적어야 합니다.**
57개의 ALTER 블록이 바로 그 손으로 적은 것들입니다. 그리고 **31개를 빠뜨렸습니다.**

### 구체적 피해 3가지

| # | 피해 | 언제 터지나 |
|---|------|-------------|
| **1** | **DB를 재구축할 수 없음** — 뭐가 나올지 아무도 모름 | 장애 복구 · 서버 이전 · 스테이징 복제 · 신규 테넌트 온보딩 |
| **2** | **다음 컬럼 추가가 운영에서만 조용히 실패** | 다음 스키마 변경 때. **로컬은 통과하므로 배포 후에야 발견** |
| **3** | **alembic autogenerate 사용 불가** | 자동 생성을 돌리면 아는 그림(8종)과 실제(21종) 차이를 "삭제해야 할 것"으로 판단 → **테이블 DROP 마이그레이션이 나올 수 있음** |

> 🔴 피해 3이 가장 위험합니다. 나중에 누군가 "이제 alembic 제대로 쓰자"며
> `alembic revision --autogenerate` 를 돌리고 무심코 적용하면 **운영 테이블이 지워집니다.**
> 이 프로젝트를 끝내기 전까지는 **autogenerate 를 절대 쓰면 안 됩니다.**

## 3. 왜 리팩토링과 분리하나 · 왜 리팩토링 "후"인가

### 분리하는 이유

| | |
|---|---|
| **리팩토링은 스키마를 안 건드립니다** | 파일 이동 + import 경로 변경뿐. `models.py` 는 통째로 `shared/storage/` 로 이동만 (내용 0줄 수정) |
| **섞으면 원인 추적이 불가능해집니다** | 리팩토링 중 장애가 나면 "파일을 옮겨서인가 스키마를 건드려서인가"를 구분할 방법이 없습니다 |
| **검증 방식이 완전히 다릅니다** | 리팩토링 = 코드 테스트 + diag 시퀀스 대조 / 스키마 = **운영 DB 실물 대조**. 안전망이 겹치지 않습니다 |
| **되돌리는 방법이 다릅니다** | 리팩토링 = `git revert` 로 끝 / 스키마 = **되돌릴 수 없음** (DDL은 롤백이 어렵고 데이터가 걸림) |

### "후"인 이유

| | |
|---|---|
| 급하지 않음 | 지금 운영은 정상입니다. 터지는 시점은 **"다음 스키마 변경 때"** 입니다 |
| 리팩토링을 막지 않음 | 리팩토링에 필요한 건 `models.py` 를 옮기는 것뿐 |
| 먼저 하면 리팩토링이 몇 주 밀림 | 운영 DB 덤프·대조·검증은 신중하게 해야 하는 작업입니다 |

### ⚠️ 단, 리팩토링 기간 중 지켜야 할 것

> **리팩토링이 끝날 때까지 스키마를 변경하지 마세요.**
> 컬럼을 추가해야 하는 기능이 생기면, 이 프로젝트를 먼저 끝내거나
> 최소한 **`init_db` ALTER 블록에 반드시 추가**하고 운영 반영을 확인하세요.

## 5. 단계

> **모든 단계는 운영 DB에 손대기 전에 스테이징(운영 덤프 복제본)에서 먼저.**

| # | 단계 | 산출물 | 위험 |
|---|------|--------|------|
| **S1** | **운영 DB 실제 스키마 덤프** — 테이블·컬럼·타입·제약·인덱스 전수 | `schema-prod.sql` (또는 JSON) | 없음 (읽기 전용) |
| **S2** | **3자 대조** — 운영 실물 × `models.py` × alembic head. 차이를 전수 표로 | `schema-diff.md` | 없음 |
| **S3** | **판정** — 차이마다 ⓐ 모델이 맞음(=DB에 추가) ⓑ DB가 맞음(=모델 수정) ⓒ 레거시(=삭제) | 판정표 | **사람 판단** |
| **S4** | **baseline 마이그레이션 1개 생성** — 운영 실물과 정확히 일치하는 `create_all` 스냅샷 | `alembic/versions/XXXX_baseline.py` | 🟨 |
| **S5** | **alembic 히스토리 재출발** — 기존 35개를 archive 로 접고 baseline 을 새 시작점으로. 운영 DB엔 `alembic stamp` | | 🟧 |
| **S6** | **스테이징 검증** — 빈 DB → `alembic upgrade head` → 운영 덤프와 diff | diff = 0 | 🟧 |
| **S7** | **`init_db` 해체** — ALTER 57개 + `create_all` 제거. `init_db` 는 시드만 담당 | `database.py` 축소 | 🟥 |
| **S8** | **재발 방지 가드** — 모델 컬럼 ↔ 마이그레이션 대조를 CI 에서 검사 | `scripts/arch/check_schema.py` | 없음 |

### S3 이 이 프로젝트의 본체입니다

31개 컬럼 + 8개 테이블 + 5개 유령마다 **"어느 쪽이 정답인가"** 를 사람이 판정해야 합니다.
자동으로 맞출 수 없습니다 — 운영 DB에 있는데 모델에 없는 컬럼이 나올 수도 있고, 그게 쓰는 컬럼인지 죽은 컬럼인지는 코드를 봐야 압니다.

### S8 이 이 프로젝트의 진짜 목적입니다

S1~S7 은 한 번 청소하는 것이고, **S8 이 없으면 다시 더러워집니다.**
G 그룹의 교훈이 정확히 이것입니다 — **손으로 지키면 반드시 빠뜨립니다.**

```python
# scripts/arch/check_schema.py  (개념)
# models.py 의 모든 컬럼이 alembic 마이그레이션에 근거가 있는지 검사
# 없으면 CI 실패 → "마이그레이션을 안 썼습니다"
```

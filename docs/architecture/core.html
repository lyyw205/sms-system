예약 데이터의 일생

아키텍처 맵에서 “핵심(코어)”이라고 표시한 층을 자세히 뜯어봅니다. 무엇이 왜 코어인지, 8개 부분이 각각 무슨 일을 하는지, 그리고 지금 실제로 어디서 어떻게 쓰이고 있는지를 정리했습니다.

본문은 개발 지식 없이 읽을 수 있게 썼습니다. + 개발자용 접힘 블록에 파일 위치와 실측 수치가 들어 있습니다. 수치는 모두 지금 코드를 직접 세어본 값입니다 (2026-08-23 기준).

00코어란 무엇인가

쉽게 말하면

코어는 “공통으로 쓰는 것 모음”이 아닙니다. 그렇게 정의하면 경계가 안 그어집니다 — 아무거나 두 곳에서 쓰면 코어가 돼버리니까요.

이 시스템의 코어는 “예약 데이터가 태어나서 · 정리되고 · 검사를 지나 저장되고 · 딸린 것들이 맞춰지는 한 줄기 흐름”입니다. 한마디로 예약 데이터의 일생입니다.

판정하는 방법 — 한 줄 질문

“이걸 지우면 예약 데이터가 앞뒤가 안 맞게 되는가?”

예 → 코어입니다. 아니오 → 기능(모듈)입니다. 실제로 이 질문 하나로 갈립니다.

코어는 “안 바뀌는 곳”이 아닙니다

업무 규칙이 바뀌면 코어는 바뀝니다 — 파티 기준이 바뀌거나, 밤 계산 규칙이 바뀌면요. 업무 규칙이 바뀌어도 안 바뀌는 것(로그인·설정·데이터베이스 연결·기록)은 코어가 아니라 그 아래 바탕 층입니다. 이 둘을 한 곳에 두면 “코어는 안정적”이라는 말이 말로만 남습니다.

01예약 하나의 일생

쉽게 말하면

예약 한 건이 들어와서 사라질 때까지 거치는 여덟 단계입니다. 각 단계마다 코어의 어느 부분이 일하는지를 오른쪽에 붙였습니다. 이 그림이 이 문서의 지도입니다.

쉽게 말하면

코어 안에서도 위아래가 있습니다. 맨 아래는 아무도 안 부르고 계산만 하는 것(어휘 사전, 달력), 가운데는 검사하고 저장하는 관문, 맨 위는 순서를 지휘하는 것입니다. 위가 아래를 부르고, 아래는 위를 모릅니다.

어휘 사전

core/vocabulary

“이게 무엇인가”를 판정하는 말뭉치입니다. 예약 하나가 들어왔을 때 배정 대상인가 · 숙박 손님인가 · 밤이 있는가 · 파티에 참여하는가 · 등급이 몇인가를 여기서 답합니다.

예를 들어 액티비티(투어·체험) 예약은 사람은 오지만 방에서 자지 않습니다. 그래서 “배정 대상 아님 · 숙박 인원 통계에서 제외 · 밤 0개 · 연박 불가”라는 성질을 갖습니다. 이런 판정이 예전엔 코드 30여 곳에 각각 적혀 있었고, 지금은 명세서 한 곳에 모여 있습니다.

예약 관문

core/reservation

예약 값을 바꾸려는 모든 시도가 지나야 하는 문입니다. 그리고 예약을 화면에 보여줄 때 한 벌로 만들어 내보내는 곳이기도 합니다.

문에서 묻는 건 두 가지입니다. “누가 바꾸려 하는가”(네이버 자동 / 직원 손 / 시스템 내부)와 “이 자리에 건드리지 마 스티커가 붙어 있는가”. 예를 들어 직원이 퇴실일을 연장해 두면 네이버가 옛날 값을 보내와도 통과시키지 않습니다.

들어 있는 것
변경 권한표(필드 × 출처 = 허용 / 조건부 / 금지) · 이사 예정 날짜 바뀌면 일자별 기록 평행이동 · 이사 예정 화면 응답 만들기
지금 쓰임
변경 권한표는 3개 파일만 사용 중이고 우회가 24곳 있습니다 — 관문을 만들어 놓고 아직 강제하지 않아서입니다. 반면 화면 응답 만들기는 24곳에서 호출됩니다. 예약이 화면에 보이는 모든 경로가 여기를 지납니다.
왜 코어
응답 만들기가 코어인 이유가 흥미롭습니다 — “문자 예약표를 화면에 어떻게 표시할지” 규칙이 전부 여기 들어 있기 때문입니다. 예를 들어 연박으로 묶인 다른 예약이 어제 보낸 문자도 오늘 화면에 “발송 완료”로 보여줘야 하는데, 그 판단이 여기 있습니다. 두 벌로 만들면 화면마다 다르게 보입니다.
정리 후
우회 24곳을 흡수한 뒤 문을 잠급니다 — 우회하면 즉시 오류가 나게. 이게 정리 전체의 최종 목표 중 하나입니다.

④

문자 예약표

core/chip

“이 손님에게 · 이 문자를 · 이 날 보낸다”를 적어둔 표를 만들고 지키는 부분입니다. 표의 한 줄을 “칩”이라고 부릅니다.

예약이 바뀌면 이 표를 처음부터 다시 계산합니다. 날짜가 바뀌면 옛 날짜 줄을 지우고 새 날짜 줄을 만들고, 방이 바뀌면 건물 조건이 걸린 문자를 다시 판정합니다.

절대 지우지 않는 두 가지

다시 계산할 때도 ① 이미 보낸 줄과 ② 사람이 직접 손댄 줄(수동 추가 · 발송 제외 · 발송 실패 기록)은 건드리지 않습니다. 이게 없으면 재계산 한 번에 같은 문자가 두 번 나가거나, 빼놓은 손님에게 다시 나갑니다.

들어 있는 것
칩 만들기·지우기 단일 창구(보호 규칙 포함) · 발송 결과 기록 · 두 방향 재계산(예약 한 건 기준 / 스케줄 한 개 기준)
지금 쓰임
12개 파일이 칩 창구를 씁니다. 만들기 11곳 · 지우기 11곳. 예전엔 17개 파일이 각자 칩을 직접 만들고 지웠는데, 지금은 창구 하나로 모였습니다 — 코어 중 정리가 가장 잘 된 곳입니다.
왜 코어
예약·객실배정·문자 스케줄 셋 다에 딸린 파생물이라 어느 한쪽 소유가 아닙니다.
정리 후
이것도 문을 잠급니다. 지금은 우회가 0건이지만 “우연히” 0건이라, 규칙이 아니라 관례로 지켜지는 상태입니다.

여기에 알려진 결함이 하나 있습니다

템플릿을 비활성화할 때 칩을 일괄 삭제하는 코드에 “우리 지점만”이라는 조건이 빠져 있습니다. 두 지점이 같은 템플릿 이름을 쓰는 상태에서 한쪽이 끄면 다른 지점의 칩까지 지워지고, 되돌릴 수 없으며, 흔적도 남지 않습니다. 정리 계획에서 가장 먼저(코드 이동 전에) 고칠 항목으로 잡혀 있습니다.

뒷정리 순서표

core/lifecycle

예약에 무슨 일이 생기면 뒤따라 해야 할 일들을 정해진 순서로 실행하는 지휘자입니다. 코어에서 가장 많이 불리는 부분입니다.

다섯 가지 사건에 각각 반응합니다 — 날짜가 바뀜 · 인원/성별이 바뀜 · 취소됨 · 방이 배정됨 · 예약이 삭제됨. 예를 들어 날짜가 바뀌면 ① 파티 체크인과 일자별 메모를 평행 이동 → ② 배정표에서 범위 밖 날짜를 지우고 빠진 날짜를 채움 → ③ 보낼 문자 목록 5종을 전부 다시 계산, 이 순서로 돕니다.

순서가 진짜로 중요합니다

문자 목록 계산을 방 배정보다 먼저 하면 안 됩니다. “○○동 손님에게만” 같은 조건이 걸린 문자는 방이 정해지기 전에는 대상을 고를 수 없어서, 칩이 아예 안 만들어집니다. 그래서 이 순서는 취향이 아니라 데이터 의존이고, 코어가 순서를 글로 선언하는 이유입니다.

들어 있는 것
5가지 사건별 후처리 · 문자 목록 5종 일괄 재계산 · 신설 예정 순서 선언표와 특수 문자 등록소
지금 쓰임
일괄 재계산은 20곳에서 호출됩니다 — 서비스 6곳(배정·동기화·분할 정합) + 화면 API 14곳(예약 수정·방 배정·연박 연장·방 설정 변경). 예약을 건드리는 거의 모든 경로가 여기로 모입니다.
왜 코어
여기가 없으면 예약은 바뀌었는데 딸린 것들은 옛날 상태로 남습니다. 정의상 데이터 부정합입니다.
정리 후
지금은 기능들이 직접 서로를 부릅니다. 정리 후에는 기능이 “예약 동기화됨” 같은 신호만 보내고, 이 순서표가 등록된 순서대로 실행합니다 (→ 아키텍처 맵 §04-3).

⑦

방 찾기

core/lookup

“이 예약들이 어느 방이었지?”를 한 번에 물어보는 창구입니다. 작지만 성능에 중요합니다.

예약 100건을 화면에 보여줄 때 방 정보를 하나씩 100번 물어보면 화면이 느려집니다. 여기는 100건을 한 번에 물어봅니다. 그리고 날짜를 지정하지 않으면 “첫 밤의 방”을 돌려주는 규칙이 정해져 있어, 호출하는 쪽마다 다른 답을 받는 일이 없습니다.

지금 쓰임
3개 파일에서 사용 — 예약 목록 · 문자 변수 계산 · 화면 응답.
왜 코어
“어느 방인가”는 예약 데이터의 파생 상태이고, 여러 도메인이 같은 답을 받아야 하기 때문입니다.
개발자용

services/room_lookup.py(76) — batch_room_lookup · batch_room_number_map. target_date=None이면 order_by(date)로 가장 이른 배정을 결정적으로 선택(첫 밤 기준). 특정 날짜가 필요하면 호출자가 target_date를 명시해야 합니다.

⑧

바깥 연결 규격

core/ports

“이런 모양이면 꽂을 수 있다”는 콘센트 규격입니다. 네이버든 문자 발송 업체든, 이 규격에 맞기만 하면 코어는 상대가 누구인지 몰라도 됩니다.

“죽은 코드처럼 보이지만 지우면 안 되는 것”

이 규격은 원래 가짜(연습용) 연결과 진짜 연결을 바꿔 끼우려고 만들었는데, 가짜 쪽이 전부 삭제되면서 지금은 구현이 하나뿐입니다. 그래서 “쓸모없는 추상화”로 보여 삭제 후보에 올랐었습니다.

실제로 확인해 보니 테스트 3개가 이 규격으로 가짜 연결을 끼우고 있었습니다. 지웠다면 테스트가 실제 문자 발송 업체를 호출해서 손님에게 문자가 나갔을 것입니다. → 삭제가 아니라 코어의 포트로 승격하는 것으로 결론이 바뀌었습니다.

들어 있는 것
문자 발송 규격 · 예약 조회 규격 · 신설 예정 방 배정 규격
정리 후
방 배정 규격이 생기면, 배정 기능을 떼어내도 시스템이 안 깨집니다 — 꽂힌 게 없으면 호출한 쪽이 “배정 기능 없음”이라고 정해진 대로 처리합니다.
개발자용

providers/base.py(77) — SMSProvider(send_sms·send_bulk·simulate_receive) · ReservationProvider(sync_reservations·get_reservation_details·fetch_by_checkin_date). 신설 RoomAllocator.assign(db, reservation_id, room_id, dates) -> AssignResult, get() -> RoomAllocator | None.

배치는 core/ports(규격) / adapters/{aligo,naver}(구현) / bootstrap/factory.py(꽂기). Protocol을 지우면 코어가 real/sms.py·real/reservation.py를 직접 import 하게 되어 계층이 무너집니다.

04코어가 아닌 것 — 경계선

쉽게 말하면

헷갈리기 쉬운 것들입니다. 중요하다고 코어인 건 아닙니다. 네이버 동기화는 이 시스템의 존재 이유지만 코어가 아닙니다 — 없으면 예약이 안 들어올 뿐, 이미 있는 데이터가 어긋나지는 않기 때문입니다.

이건코어일 것 같지만실제로는
빈 방 찾아 넣기
(자동 배정 알고리즘)		 객실 배정은 핵심 업무니까 기능. 없으면 손으로 배정하면 됨 — 데이터는 멀쩡. 조사 결과 25개 함수가 그대로 기능에 남습니다 = 진짜 독립 모듈
네이버에서 가져오기 시스템의 존재 이유니까 기능 + 어댑터. 예약을 “만들어 넣는” 입구일 뿐. 정리 후 가장 먼저 떼어낼 후보
추가요금 · 파티 안내 MMS
업그레이드 약속/후기		 문자 관련이니 코어 아닌가 기능. 다만 등록소에 자기를 꽂아 코어가 필요할 때 불러줌. 지금은 반대로 코어가 이들을 직접 부르고 있어서 26곳에 얽힘
도미토리 남녀 분리 잠금 중요한 규칙이니까 기능. 배정 “결정”에 속하는 규칙
연박 감지 · 분할 예약 정합 예약 데이터를 만지니까 기능(준필수). 다만 지금 11곳이 붙잡고 있어 떼기 어려움
로그인 · 지점 격리 · 설정 · 기록 모두가 쓰니까 코어 아닌가 바탕 층. 업무 규칙이 바뀌어도 안 바뀝니다. 여기에 “예약”·“문자”·“파티” 같은 단어가 나오면 잘못 놓인 것
대시보드 · 매출 · 파티 체크인 — 기능. 예약을 읽기만 하는 말단이라 지금도 떼어낼 수 있습니다

계산이 예상을 반박한 사례

조사할 때 구역 명세서를 코어라고 가정했는데, 실제로 세어 보니 함수마다 특정 기능 전용이었습니다 (명세서 패턴이라 코어처럼 보였을 뿐). 반대로 “그날 있는 예약” 판정은 6개 도메인이 써서 코어 1순위인데도 문자 스케줄 필터 파일 안에 갇혀 있었습니다.

코어를 느낌이 아니라 “몇 개 도메인이 쓰는가”로 계산한 이유입니다.

05코어 안에서 합치면 안 되는 것

쉽게 말하면

“정리”라고 하면 비슷한 걸 합치고 싶어집니다. 그런데 겉보기엔 중복인데 실제로는 달라야 하는 것들이 있습니다. 합치면 그 자리에서 사고가 납니다. 코어 안에서 특히 조심해야 할 것들입니다.

겉보기합치면왜 달라야 하나
파티 참여 집합 두 개
(1차만·1+2차·2차만) vs (1+2차·2차만)		 오발송 / 통계 누락 앞은 파티 참여 통계·명단용, 뒤는 2차 안내 MMS 대상용. 넓은 쪽으로 합치면 1차만 신청한 손님에게 2차 안내가 갑니다. 좁은 쪽으로 합치면 통계에서 사람이 빠집니다
빈 값 처리 3가지
(파티 차수의 일자별 덮어쓰기)		 화면·통계·문자 대상이 조용히 달라짐 파이썬 쪽은 NULL과 '' 둘 다 원래 값으로 되돌리고, SQL 쪽은 NULL만 되돌리며 ''는 그대로 씁니다. 의도된 차이입니다
배정 충돌 정책 두 가지 배정 사고 방 배정은 충돌 시 기존 손님을 밀어내고, 날짜 정리는 밀어내지 않고 공존시킵니다. 둘 다 맞습니다
숙박일 판정의 “이상한” 동작
(퇴실일이 입실일보다 앞선 손상 데이터)		 동작 변화 지금은 그런 행을 연박으로 취급합니다. 이상해 보이지만 현행 동작을 그대로 보존하는 게 원칙 — 고칠지는 옮긴 뒤에 따로 결정합니다

원칙: 현행 보존

코어를 옮기는 동안에는 “이상해 보이는 것”을 고치지 않습니다. 옮기기와 고치기를 섞으면, 문제가 생겼을 때 옮겨서 깨진 건지 고쳐서 깨진 건지 알 수 없습니다. 먼저 자리를 잡고, 그다음에 하나씩 결정합니다.

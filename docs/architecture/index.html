04제각각인 파이프라인 3가지

쉽게 말하면

같은 질문에 답하는 방법이 여러 벌로 존재합니다. 두 벌이 조금씩 다르게 답하면 문자가 안 나가거나 유령 데이터가 남습니다. 대표적인 3가지를 그림으로 봅니다.

4-1. “며칠 묵나” 계산이 54곳에 흩어져 있다

이 시스템이 실제로 쓰는 단위는 “밤”입니다(4/10~4/12 예약이면 밤은 4/10, 4/11 두 개). 그런데 저장은 체크인·체크아웃 날짜로 되어 있어, 쓸 때마다 변환해야 합니다. 그 변환 규칙이 함수 54개에 각각 복사돼 있습니다.

개발자용 — 근거 수치

check_out_date 조건 47곳 전수 분류: 경계 계산 20 · 밤 목록(-timedelta(1)) 26 · 당일1박 판정 3 · 연박 이어붙이기 5 · 분할 형제 식별 1 · 체크아웃날 자체를 타겟으로 쓰는 곳 0. check_in_date/check_out_date를 만지는 함수 54개 · 파일 24개.

설계: Stay(예약 1건의 밤들) / StayChain(연박 그룹의 밤들). date_target='today_checkout'은 이미 legacy 처리되어 today로 강등 중이고, 체크아웃이 의미 있는 유일한 도메인(청소)조차 어제와 오늘 배정이 모두 존재하는가로 판정합니다 — 시스템은 이미 밤 기반으로 옮겨왔고 개념만 명시되지 않았습니다. 문서: docs/plans/refactor/05-stay-개념설계.md

4-2. 네이버가 안 바꿨는데도 5분마다 덮어쓰기를 시도한다

직원이 인원을 5명으로 고쳐 놓으면, 5분 뒤 동기화가 네이버의 옛날 값 4명으로 되돌리려 합니다. 네이버 쪽은 아무것도 바뀌지 않았는데도요. 이걸 막으려고 보호 표시가 7종·68곳으로 번식했습니다.

4-3. 기능이 다른 기능의 뒷정리를 직접 시킨다

네이버 동기화가 끝나면 연박 묶기 → 방 배정 → 문자 예약표 → 즉시 발송 순서로 뒷정리가 필요합니다. 지금은 동기화 코드가 이 넷을 직접 하나씩 부릅니다. 그래서 순서를 알려면 코드를 읽어야 하고, 넷 중 하나를 떼어내면 동기화가 깨집니다.

05진짜 문제 — 안전장치가 잠겨 있지 않다

쉽게 말하면

이 시스템에는 지켜야 할 안전장치가 8개 있습니다. “예약 수정은 이 문으로만”, “문자 예약표는 이 문으로만” 같은 것들입니다. 그런데 실제로 잠겨 있는 문은 1개뿐이고, 나머지 7개는 “이 문으로 다니세요”라는 안내문일 뿐입니다.

결과는 놀랍도록 단순합니다 — 잠근 문은 우회 0건, 안내문만 붙인 문은 전부 우회됐습니다. 같은 저장소, 같은 사람이 짰는데도요.

잠그기 전에 반드시 확인할 것

우회에는 두 종류가 있고 처방이 정반대입니다. (가) 지킬 수 있는데 안 지킨 것은 잠그면 해결됩니다. (나) 문이 그 기능을 안 담고 있어서 못 지킨 것은 잠그면 정당한 작업이 막힙니다.

실제 사례 — 네이버 연동 관련 우회 9곳은 전부 (나)였습니다(아직 저장 안 한 쿠키를 검증하는 경우 등). 그냥 잠갔다면 쿠키 검증 기능이 통째로 막혔을 것입니다. 그래서 잠그기 전에 문을 먼저 넓히는 단계가 계획에 들어 있습니다.

쉽게 말하면

07가는 길

쉽게 말하면

한 번에 다 바꾸지 않습니다. 단계마다 되돌릴 수 있게, 그리고 동작이 하나도 안 바뀌었음을 자동으로 확인하면서 갑니다. 순서에는 이유가 있습니다 — 예를 들어 안전장치 잠그기는 맨 마지막입니다. 먼저 잠그면 우회하던 24곳이 한꺼번에 터지기 때문입니다.

지금 당장 할 수 있는 것 / 막혀 있는 것

바로 가능 — 누수 결함 2건 차단(5줄), 그리고 위험이 큰 4개 영역에 “현재 동작을 그대로 고정하는 테스트” 보강. 이 둘은 코드 이동 전에 끝나 있어야 합니다.

막혀 있음 — “이건 의도인가 실수인가” 판단이 필요한 항목들. 예를 들어 예약 ‘생성’은 관문을 안 거치고 ‘수정’만 거치는데 의도인지, 더블룸 판정용 상품번호가 코드에 직접 적혀 있는데 설정으로 뺄지 같은 것들입니다. 어느 쪽이 정답인지 모르면 두 벌인 코드를 합칠 수 없습니다.

절대 건드리면 안 되는 것들이 있습니다

조사에서 확인된 사실 하나 — 겉보기엔 이상한데 실제로는 사고를 막고 있는 코드가 아주 많습니다. 모르고 “정리”하면 그 사고가 다시 납니다. 예를 들면:

  • 방 배정은 충돌 시 기존 손님을 밀어내고, 날짜 정리는 밀어내지 않고 공존시킵니다. 둘 다 맞습니다 — “통일”하면 사고입니다.
  • 분할 예약 개수를 셀 때 취소된 것도 포함합니다. 살아있는 것만 세면 정리 직후부터 영원히 잘못된 경보가 뜹니다.
  • 네이버 시각을 읽을 때 시간대를 제거해야 합니다. 변환하면 9시간이 밀리고, 안 떼면 5분마다 전체 행이 쓸데없이 갱신됩니다.
  • 자동 작업 시각(09:43 → 09:50 → 09:55 → 10:01)에도 이유가 있습니다. 순서를 바꾸면 두 가지 이유가 다 깨집니다.

전수조사를 먼저 한 이유가 이것입니다 — 이런 게 수백 개입니다.

10용어 사전

문서에 나오는 낯선 말들을 이 시스템의 업무 언어로 바꿔 적었습니다.

안전장치 (관문)gate
“이 작업은 반드시 이 문으로만 지나가야 한다”는 규칙. 잠긴 문은 우회하면 즉시 오류가 나고, 안내문뿐인 문은 그냥 지나칠 수 있습니다. 지금 8개 중 1개만 잠겨 있습니다.
우회bypass
정해진 문을 안 거치고 지름길로 처리한 코드. 급할 때 생기고, 나중에 사고의 원인이 됩니다.
붙잡혀 있다inbound edge
다른 기능이 이 기능을 직접 부르고 있다는 뜻. 붙잡는 곳이 많을수록 그 기능을 손대기 어렵습니다.
층layer
코드를 성격별로 나눈 단계. 바탕(안 바뀌는 것) → 핵심(업무 규칙) → 기능(개별 업무) 순으로 쌓고, 위에서 아래로만 부릅니다.
순서표훅 레지스트리 · hooks
“예약이 동기화되면 ① 연박 묶기 ② 방 배정 ③ 문자 예약표 ④ 즉시 발송 순으로 처리한다”를 한 곳에 글로 적어둔 것. 기능이 서로를 직접 부르지 않아도 됩니다.
포트 / 어댑터port / adapter
포트 = “이런 모양이면 꽂을 수 있다”는 규격. 어댑터 = 그 규격에 맞춘 실제 연결(네이버·알리고). 규격만 정해두면 실제 연결을 바꿔 끼울 수 있습니다.
등록소레지스트리 · registry
“이런 종류의 특수 문자가 있다”를 한 곳에 모아둔 명단. 기능이 자기를 여기 등록하면, 부르는 쪽은 개별 기능을 몰라도 됩니다.
숙박 (밤)Stay · night
손님이 실제로 자는 날. 4/10~4/12 예약이면 밤은 4/10·4/11 두 개입니다. 시스템이 실제로 쓰는 단위지만 저장은 체크인/체크아웃 날짜로 되어 있어 매번 변환이 필요합니다.
문자 예약표 (칩)chip
“이 손님에게 · 이 문자를 · 이 날 보낸다”를 적어둔 한 줄. 예약이 바뀌면 다시 계산되지만, 이미 보낸 줄과 사람이 손댄 줄은 지우지 않습니다.
보호 표시핀 · pin
운영자가 손으로 고친 자리에 붙는 “건드리지 마” 스티커. 지금 7종이 68곳에 흩어져 있습니다.
지점 구분멀티테넌트 · multi-tenant
한 시스템으로 여러 게스트하우스를 운영할 때 서로의 데이터가 섞이지 않게 막는 장치. 이 시스템에서 유일하게 제대로 잠긴 문입니다(조회 한정).
동작이 안 바뀜no-op
코드 위치나 모양만 바꾸고 실제 동작은 하나도 안 바뀌는 변경. 각 단계를 이렇게 만들면 문제가 생겨도 되돌리기 쉽습니다.
되돌리기revert · rollback
방금 한 변경을 없던 일로 하고 이전 상태로 복구하는 것.
현재 동작 고정 테스트특성화 테스트
“지금 이렇게 동작한다”를 그대로 기록해두는 검사. 옳은지 그른지를 따지지 않고 바뀌었는지만 봅니다. 코드를 옮기기 전에 깔아두면 실수를 즉시 잡습니다.
발자국 기록diag
시스템이 어느 단계까지 어떻게 진행했는지 남기는 기록. 199종이 있고, 정답지와 매일 비교해서 동작이 바뀌면 잡아냅니다.
숨긴 참조지연 import
기능끼리 서로 물고 물려 프로그램이 안 뜨는 걸 피하려고, 참조를 함수 안쪽으로 밀어 넣은 것. 지금 239건 — 이미 얽혔다는 신호입니다.

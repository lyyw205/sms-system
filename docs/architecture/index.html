SMS 시스템 아키텍처 맵

지금 이 시스템이 어떻게 생겼는지, 화면의 각 탭 뒤에서 무슨 일이 일어나는지, 그리고 앞으로 프로그램을 여러 조각으로 나눈다면 어디를 자르고 어디는 붙여둬야 하는지를 정리한 문서입니다.

이 문서 읽는 법

  • 본문은 개발 지식 없이 읽을 수 있게 썼습니다. 그림과 표만 따라가도 전체 구조가 잡힙니다.
  • 쉽게 말하면 표시가 붙은 파란 상자는 그 절의 요약입니다. 시간이 없으면 이것만 읽어도 됩니다.
  • + 개발자용 이라고 접혀 있는 블록은 눌러야 펼쳐집니다. 코드 파일 위치·조건이 들어 있으니 필요할 때만 여세요.
  • 모르는 단어가 나오면 맨 아래 용어 사전을 보세요.

00이 시스템이 하는 일

쉽게 말하면

“네이버에 들어온 예약을 대신 지켜보다가, 방을 배정하고, 때가 되면 손님에게 문자를 보내주는 직원”입니다. 사람이 하면 하루 종일 붙어 있어야 하는 일 — 예약 확인, 방 배정, 안내 문자 발송 — 을 자동으로 처리합니다.

시스템이 하루 동안 하는 일을 순서대로 보면 이렇습니다.

언제무슨 일을 하나왜 필요한가
5분마다 네이버에 새 예약·변경·취소가 있는지 확인해서 우리 장부에 옮겨 적음 네이버는 예약이 들어와도 우리에게 먼저 알려주지 않음 — 계속 물어봐야 함
새 예약이 들어오면 연박 손님인지 확인 → 방 자동 배정 → 보낼 문자 목록 갱신 → 즉시 안내 문자 발송 예약 하나가 들어오면 뒤따라 해야 할 일이 줄줄이 있음
매일 오전 9:55 놓친 예약 재확인 → 10:01 오늘·앞으로의 객실 자동 배정 운영자가 출근했을 때 이미 배정이 끝나 있게
설정한 시각마다 템플릿에 맞춰 손님에게 문자 자동 발송 (체크인 안내, 비밀번호, 파티 안내 등) 일일이 손으로 보내지 않기 위해
현장에서 파티 입장 체크, 청소 대상 확인, 매출 조회를 직원이 화면에서 처리 현장 업무도 같은 예약 데이터를 봐야 함

이 모든 일이 지금은 프로그램 딱 한 개 안에서 돌아갑니다. 그 프로그램 안에 화면 요청을 받는 창구, 실제 일을 처리하는 부서들, 정해진 시각에 일을 시키는 알람시계가 전부 들어 있습니다.

01지금 구조 — 한 덩어리 프로그램

쉽게 말하면

사무실 하나에 책상 하나뿐인 상태입니다. 손님 응대(화면 요청), 실무 처리(예약·배정·문자), 알람시계(자동 실행)가 전부 그 책상 위에 있습니다.

일이 잘 돌아갈 땐 문제없지만, 책상을 정리하려고 잠깐 치우면 그동안 전화도 못 받고 알람도 안 울립니다. 실제로 프로그램을 새로 배포하는 순간 5분 자동 동기화도 같이 멈춥니다. 이게 지금 구조의 가장 큰 불편입니다.

03왜 쪼개려는 걸까

쉽게 말하면

“마이크로서비스”란 지금 한 덩어리인 프로그램을 여러 개의 작은 프로그램으로 나누는 것입니다. 한 사무실 한 책상에서 다 하던 일을, 창구·실무·알람 담당을 각각 다른 방으로 옮기는 것과 같습니다.

나누면 한 방을 고치는 동안 다른 방은 계속 일할 수 있습니다. 대신 방끼리 서류를 주고받아야 해서 전보다 복잡해집니다. 그래서 “전부 나누기”가 아니라 나눌 값어치가 있는 것만 나눠야 합니다.

지금 불편한 점 3가지

불편지금 무슨 일이 벌어지나나누면 어떻게 되나
고칠 때 전부 멈춘다 화면 문구 하나 고치려고 프로그램을 새로 올리면, 그 사이 5분 자동 동기화도 같이 멈춤 화면 담당만 재시작하고 동기화는 계속 돌아감
한 곳이 아프면 다 아프다 네이버 쪽이 느려지거나 로그인 쿠키가 만료되면 그 여파가 프로그램 전체에 걸림 네이버 담당만 힘들어하고 나머지는 평소대로
바쁜 곳만 키울 수 없다 문자 발송이 몰릴 때 그 부분만 늘리지 못하고 프로그램 전체를 늘려야 함 발송 담당만 여러 명으로 늘림

다만, 나누면 새로 생기는 어려움도 있습니다

한 방에서 다 하던 때는 “이건 되고 저건 안 됐다”가 생길 수 없었습니다. 실패하면 통째로 없던 일이 됐으니까요. 방을 나누면 “예약은 저장됐는데 방 배정은 실패한” 어중간한 상태가 실제로 생깁니다. 그래서 아래 §04에서 절대 나누면 안 되는 묶음을 먼저 정합니다.

04어떻게 쪼갤 것인가

쉽게 말하면

예약 · 객실 배정 · 문자 예약표 이 셋은 항상 같이 계산됩니다. 손님 날짜가 하루 바뀌면 방 배정도 바뀌고 보낼 문자 목록도 바뀝니다. 한 장의 종이에 같이 적혀 있는 것이라 찢으면 앞뒤가 안 맞습니다 — 여기는 붙여둡니다.

반면 네이버에서 예약 가져오기, 로그인 관리, 기록·알림은 실패해도 예약 자체를 되돌릴 필요가 없습니다. 이런 것부터 떼어냅니다.

네이버 예약 가져오기 먼저 떼기

5분마다 네이버에 접속해 예약을 긁어오고, 우리 형식으로 정리해서 넘겨주는 역할. 네이버 쪽 장애나 쿠키 만료가 나머지에 번지지 않게 된다.

real/reservation · naver_sync · NaverBizItem

로그인 · 지점 관리 먼저 떼기

직원 계정, 권한, 어느 게스트하우스인지 구분, 네이버 연동 설정. 다른 모두가 이쪽을 읽기만 하므로 방향이 이미 한쪽이다.

auth/ · api/auth · api/tenants · api/settings

기록 · 알림 먼저 떼기

무슨 일이 있었는지 남기고, 화면을 실시간 갱신하고, 이상하면 디스코드로 알린다. 여기서 뭔가 유실돼도 예약 데이터는 멀쩡하다.

activity_logger · event_bus · diag_logger · discord_notify

예약 · 배정 · 문자 예약표 떼지 않음

이 시스템의 심장. 셋이 항상 함께 다시 계산되므로 나누는 순간 “예약은 됐는데 방은 안 잡힌” 상태가 실제로 생긴다. 보호 대상이다.

reservation_mutator · reservation_lifecycle · room_assignment · chip_reconciler · reconcile

문자 실제 발송 나중에

“누구에게 언제 보낼지 정하는 일”(예약표)과 “실제로 보내는 일”을 분리한다. 발송이 밀려도 예약 처리는 계속된다.

sms_sender · real/sms · templates/renderer

현장 업무 나중에

파티 체크인·매출·청소·호스트. 예약을 보기만 하고 결과는 자기 기록에 남긴다. 예약 조회 창구만 정리되면 뗄 수 있다.

party_checkin · party_hosts · daily_host · sales_report · cleancrew

자동 알람시계 나중에

지금은 본체 안에 있어서 프로그램을 새로 올리면 자동 작업도 멈춘다. 이걸 따로 빼는 것만으로 현재 가장 큰 불편이 사라진다.

scheduler/jobs · schedule_manager · template_scheduler

05먼저 풀어야 할 매듭 3가지

쉽게 말하면

나누기 전에 지금 구조가 몰래 의존하고 있는 것 3개를 먼저 풀어야 합니다. 이걸 안 풀고 나누면 데이터가 섞이거나 같은 문자가 두 번 나가는 사고가 납니다.

매듭지금 어떻게 되어 있나그냥 나누면 무슨 일이 나나먼저 할 일
지점 구분
가장 위험		 “지금 처리 중인 게 어느 게스트하우스 것인지”를 프로그램이 속으로 기억하고 있고, 모든 조회에 자동으로 붙는다 프로그램이 나뉘면 그 기억이 따라가지 않는다 → A지점 직원에게 B지점 예약이 보일 수 있다 지점 번호를 “몰래 기억”이 아니라 주고받는 서류에 반드시 적힌 항목으로 만들고, 받는 쪽도 확인
함께 계산되는 심장부
보호 대상		 예약·배정·문자 예약표가 한 번에 다 되거나 한 번에 다 취소되도록 묶여 있다 “문자 예약표는 만들어졌는데 방 배정은 취소된” 어긋난 상태가 실제로 발생 나누지 않는다. 대신 같은 작업을 여러 번 반복해도 결과가 같도록 유지
본체 안의 알람시계
배포 불편		 자동 작업 14개와 실시간 알림이 본체 프로그램 안에 있다 본체를 여러 개로 늘리면 같은 자동 작업이 여러 번 실행된다 (문자 중복 발송 위험) 알람시계를 별도 프로그램으로 빼고, “이 작업은 한 명만 실행” 잠금 장치 추가

권고 순서 — 3번까지만 해도 대부분 해결됩니다

1) 지점 번호를 명시적으로 주고받도록 전환 → 2) 실시간 알림 통로를 본체 밖으로 → 3) 알람시계 분리 → 4) 네이버 가져오기 분리 → 5) 로그인·기록 분리 → 6) 문자 발송·현장 업무 분리.

3번까지만 해도 “프로그램을 새로 올리면 자동 동기화가 멈춘다”는 현재 가장 큰 운영 리스크가 사라집니다. 실익의 대부분은 4번 이전에 회수됩니다 — 무리해서 끝까지 갈 필요가 없다는 뜻입니다.

심장부 트랜잭션 services/reconcile.py::reconcile_all_chips() — 표준칩 + surcharge + party3 + upgrade ×2 를 한 커밋 분해 대상 아님. 외부 이벤트 재전송에 대비해 멱등 재계산 성질 유지
인프로세스 스케줄러 scheduler/jobs.py (APScheduler 14잡) · services/event_bus.py (메모리 큐) 잡 워커 프로세스 분리 + 분산 잡 락, 이벤트 버스를 Redis Pub/Sub 등으로 외부화

08용어 사전

문서에 나오는 낯선 말들입니다. 개발 용어를 이 시스템의 업무 언어로 바꿔 적었습니다.

동기화sync
네이버 장부와 우리 장부를 대조해서 맞추는 일. 네이버가 먼저 알려주지 않기 때문에 우리가 5분마다 물어봅니다.
대사reconcile
혹시 놓친 게 없는지 처음부터 다시 대조하는 일. 매일 오전 9:55에 오늘·내일 체크인 예약을 통째로 다시 확인합니다.
문자 예약표 (칩)chip
“이 손님에게 · 이 문자를 · 이 날짜에 보낸다”를 적어둔 한 줄. 예약이 바뀌면 이 표도 다시 계산됩니다. 이미 보낸 줄과 사람이 직접 손댄 줄은 지우지 않습니다.
재계산reconcile chips
문자 예약표를 지금 상태 기준으로 처음부터 다시 만드는 것. 조건이 바뀌었는데 옛날 표가 남아 잘못 발송되는 걸 막습니다.
지점 구분multi-tenant
한 시스템으로 여러 게스트하우스를 운영할 때, 서로의 데이터가 절대 섞이지 않게 막는 장치.
저장 확정commit
여기까지 한 작업을 장부에 확실히 기록하는 지점. 이 지점을 지나면 뒤에서 뭐가 실패해도 되돌아가지 않습니다.
되돌리기rollback
방금 하던 작업을 없던 일로 하고 원래대로 돌리는 것.
몇 번을 해도 같음멱등 · idempotent
같은 작업을 2번, 3번 반복해도 결과가 똑같은 성질. 5분마다 같은 예약을 다시 처리해도 중복이 안 생기는 이유입니다.
자동 작업job · scheduler
정해진 시각에 사람 없이 자동으로 도는 일. 현재 14가지가 등록돼 있습니다.
한 덩어리 프로그램모놀리스 · monolith
모든 기능이 한 프로그램 안에 들어 있는 형태. 지금 이 시스템의 상태입니다.
쪼갠 프로그램들마이크로서비스 · microservices
기능별로 나눈 여러 개의 작은 프로그램. 따로 고치고 따로 켤 수 있는 대신, 서로 정보를 주고받아야 해서 복잡해집니다.
대기줄큐 · queue
일감을 순서대로 세워두는 곳. 받는 쪽이 바빠도 일감이 사라지지 않게 해줍니다.
쿠키cookie
네이버에 로그인한 상태를 증명하는 열쇠. 만료되면 예약을 하나도 못 가져옵니다. 연동 설정 탭에서 갱신합니다.
대표 예약 / 딸린 예약primary / sibling
네이버에서 방 3개를 한 건으로 예약하면, 우리 쪽에서는 대표 1건 + 딸린 2건으로 나눠 저장합니다. 네이버의 변경은 대표에만 전달됩니다.
발자국 기록diag
시스템이 어느 단계까지 어떻게 진행됐는지 남기는 기록. 문제가 생겼을 때 어디서 멈췄는지 추적하는 데 씁니다.

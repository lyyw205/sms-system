00지금 구조 — 모듈러 모놀리스

현재 시스템은 단일 FastAPI 프로세스 하나와 React SPA 하나입니다. 27개 API 라우터, 34개 서비스 모듈, APScheduler(14개 잡), SSE 이벤트 버스가 같은 프로세스·같은 DB 세션 풀을 공유합니다. 멀티테넌트는 네트워크가 아니라 ContextVar + SQLAlchemy 이벤트 훅으로 격리됩니다.

이 구조의 좋은 점은 유지할 가치가 있다

모듈 경계 자체는 이미 상당히 선명합니다 — reservation_mutator(필드 변경 게이트웨이), reservation_lifecycle(후처리 게이트웨이), chip_reconciler(칩 재계산), custom_schedule_registry(비표준 발송 등록소)처럼 “한 가지 책임 + 단일 진입점” 패턴이 코드에 이미 박혀 있습니다. 마이크로서비스화는 새 경계를 발명하는 일이 아니라 이미 있는 경계를 프로세스로 승격시키는 일이어야 합니다.

03서비스 분해안 — 무엇을 떼고 무엇을 붙여둘 것인가

34개 서비스를 전부 독립 서비스로 쪼개는 건 잘못된 목표입니다. 이 시스템의 심장인 예약 · 객실배정 · SMS 칩은 하나의 트랜잭션에서 함께 재계산되기 때문에 나누는 순간 분산 트랜잭션 문제로 바뀝니다. 아래는 용접부(붙여둘 것)와 절단선(떼어낼 것)을 구분한 지도입니다.

네이버 인제스트 ① 1차

외부 폴링·파싱·정규화 전담. 코어에는 “정규화된 예약” 이벤트만 넘긴다. 쿠키 만료·레이트리밋 같은 외부 장애를 코어에서 격리.

real/reservation · naver_sync · NaverBizItem

인증 · 테넌시 ① 1차

JWT 발급/검증, 사용자·테넌트·연동 설정. 다른 모든 서비스가 읽기만 하는 의존 말단이라 방향이 이미 단방향.

auth/ · api/auth · api/tenants · api/settings

관측 · 알림 ① 1차

ActivityLog·diag·SSE·Discord. 순수 소비자이므로 유실이 코어 정합성을 깨지 않는다. 여기부터 메시지 브로커를 도입하는 게 안전.

activity_logger · event_bus · diag_logger · discord_notify

Stay Core 유지

예약 + 객실배정 + 칩. reconcile_all_chips()가 셋을 한 커밋으로 묶는다. 분해 대상이 아니라 보호 대상.

reservation_mutator · reservation_lifecycle · room_assignment · chip_reconciler · reconcile

발송 워커 ② 2차

칩 → 실제 SMS/MMS 전송. 칩 생성(코어)과 전송(워커)을 sent_at 기준으로 분리하면 큐로 뗄 수 있다.

sms_sender · real/sms · templates/renderer

현장 운영 ② 2차

파티 체크인·호스트·매출·청소. 예약을 읽기만 하고 자기 테이블에 쓴다. 읽기 계약(예약 조회 API)만 확정되면 분리 가능.

party_checkin · party_hosts · daily_host · sales_report · cleancrew

스케줄 오케스트레이터 ② 2차

지금은 API 프로세스 안의 APScheduler. 잡 실행을 별도 워커로 빼야 API 재배포가 5분 동기화를 끊지 않는다.

scheduler/jobs · schedule_manager · template_scheduler

04분해를 막는 결합 3가지

분해안을 실행하기 전에 반드시 먼저 풀어야 하는 결합입니다. 순서를 뒤집으면 사고가 납니다.

결합지금 동작왜 문제인가선행 작업
ContextVar 테넌트 격리
가장 위험		 db/tenant_context.py
before_compile / before_flush		 테넌트 필터가 프로세스 로컬 상태다. 프로세스가 나뉘면 필터가 따라가지 않고, 우회(bypass)가 유출되면 크로스 테넌트 조회가 발생한다. 테넌트 ID를 요청/이벤트 페이로드의 1급 필드로 승격하고, 서비스 간 호출마다 명시 전달 + 수신 측 검증
단일 트랜잭션 칩 재계산
코어 보호		 reconcile_all_chips()
5종 reconciler 일괄		 예약·배정·칩이 한 커밋 안에서 정합을 맞춘다. 서비스로 나누면 “칩은 생겼는데 배정이 롤백된” 상태가 실제로 발생한다. 나누지 않는다. 대신 코어 내부에서 멱등 재계산을 유지해 외부 이벤트 재전송에 안전하게 만든다
인프로세스 스케줄러 + SSE
배포 결합		 APScheduler 14잡
event_bus 메모리 큐		 API를 재배포하면 스케줄러가 함께 죽고, SSE 구독도 끊긴다. 스케일 아웃 시 잡이 중복 실행된다. 잡 워커 분리 + 분산 잡 락, 이벤트 버스를 Redis Pub/Sub 등 프로세스 외부로 이동

권고 순서

1) 테넌트 ID 명시 전달로 전환 → 2) 이벤트 버스를 프로세스 밖으로 → 3) 스케줄러 워커 분리(같은 코드베이스, 다른 프로세스) → 4) 네이버 인제스트를 독립 워커로 → 5) 인증·관측 분리 → 6) 발송 워커·현장 운영 분리.

3)까지만 해도 “재배포가 동기화를 끊는” 현재의 가장 큰 운영 리스크가 사라집니다. 마이크로서비스의 실익 대부분은 4) 이전에 회수됩니다.

문서 형식 (기준)

  • 한눈에 — 무엇을, 언제, 얼마나 자주
  • 진입점 — 자동 트리거와 수동 트리거를 모두 나열
  • 흐름도 — 단계별 코드 위치가 붙은 다이어그램
  • 단계 상세 — 각 단계가 하는 일 · 커밋 지점 · 실패 시 동작
  • 데이터 계약 — 외부 필드 ↔ DB 컬럼 매핑
  • 보호 규칙 — 운영자 수동 편집을 자동화가 덮지 않게 하는 핀
  • 진단 — diag 이벤트 목록과 운영 점검 순서
  • 서비스 분해 관점 — 이 기능이 떨어져 나갈 때의 경계와 계약

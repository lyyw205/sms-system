네이버 예약 동기화

네이버에 들어온 예약을 5분마다 확인해서 우리 장부로 옮기고, 그 뒤에 이어지는 일 — 연박 손님 묶기, 객실 배정, 보낼 문자 정리, 즉시 안내 문자 발송 — 까지 자동으로 처리하는 기능입니다. 바깥 세상이 이 시스템으로 들어오는 유일한 입구입니다.

본문은 개발 지식 없이 읽을 수 있게 썼습니다. + 개발자용이라고 접힌 블록은 코드 위치와 조건이 들어 있으니 필요할 때만 펼치세요. 모르는 말이 나오면 맨 아래 용어 사전을 보세요.

00손님 한 명을 따라가 보기

쉽게 말하면

손님이 네이버에서 예약 버튼을 누른 순간부터, 우리 시스템에서 문자가 나가기까지 실제로 무슨 일이 벌어지는지 시간 순서대로 따라가 봅니다. 이 절만 읽어도 전체 그림이 잡힙니다.

상황 — 김지현 손님이 화요일 저녁 8시 12분에 네이버에서 “2인실 2박”을 예약했습니다.

  1. 20:12

    손님이 네이버에서 예약

    이 시점에 우리 시스템은 아직 아무것도 모릅니다. 네이버는 “예약 들어왔다”고 먼저 알려주지 않습니다.

  2. 20:15

    시스템이 네이버에 물어봄

    5분마다 도는 확인 작업이 실행됩니다. “최근에 새로 등록되거나 바뀐 예약 있나요?”라고 묻고 목록을 받아옵니다. 김지현 손님 예약이 여기 들어 있습니다.

  3. 20:15

    모자란 정보를 채움

    네이버가 준 건 상품 번호와 “1건”이라는 숫자뿐입니다. 우리 장부에서 그 상품이 어떤 방인지 찾아 방 이름 · 실제 인원 · 남녀 · 도미토리 여부를 채워 넣습니다.

  4. 20:15

    우리 장부에 저장 여기부터 되돌아가지 않음

    기존에 없던 예약이므로 새로 만들어 저장합니다. 이 지점을 지나면 뒤에서 뭐가 실패해도 예약 자체는 남습니다.

  5. 20:15

    연박 손님인지 확인

    같은 이름·전화번호로 날짜가 이어지는 예약이 있으면 하나로 묶습니다. 청소팀 화면에서 “내일도 이어서 묵는 방”으로 표시되게 하기 위해서입니다.

  6. 20:15

    방 자동 배정 — 단, 오늘 체크인이면 안 함

    내일 이후 체크인이면 빈 방을 찾아 자동 배정합니다. 오후 3시 이후에 들어온 당일 체크인 예약은 자동 배정하지 않고 운영자가 직접 배정하도록 남겨둡니다 — 체크인이 코앞이라 사람 판단이 필요하기 때문입니다.

  7. 20:15

    보낼 문자 목록 갱신 저장 확정

    방이 정해진 뒤에야 “이 손님에게 · 이 문자를 · 이 날 보낸다”를 계산할 수 있습니다. 건물이나 방 조건이 붙은 문자는 배정 없이는 만들 수 없기 때문에 순서가 이렇게 정해져 있습니다.

  8. 20:15

    즉시 안내 문자 발송

    “예약 직후 보내기”로 설정된 안내가 있으면 지금 보냅니다. 이 발송이 실패해도 앞의 예약 저장은 절대 되돌리지 않습니다.

  9. 이후

    계속 지켜봄

    손님이 날짜를 바꾸거나 취소하면 다음 5분 확인 때 반영되고, 방 배정과 문자 목록도 따라서 다시 계산됩니다. 매일 오전 9:55에는 놓친 게 없는지 한 번 더 대조합니다.

여기서 기억할 것 하나

이 기능은 “예약을 받는” 기능이 아니라 “네이버 장부와 우리 장부를 계속 대조해서 맞추는” 기능입니다. 그래서 같은 예약을 5분마다 몇 번을 다시 봐도 결과가 달라지지 않도록 만들어져 있습니다.

01왜 5분마다 물어보나

쉽게 말하면

네이버가 우리에게 먼저 알려주는 기능을 제공하지 않기 때문입니다. 그래서 우리 쪽에서 계속 “새로운 거 있어요?”라고 물어보는 수밖에 없습니다.

게다가 우리가 쓰는 건 네이버가 공식으로 열어준 창구가 아니라, 네이버 사장님 페이지가 내부적으로 쓰는 통로입니다. 그래서 ①로그인 열쇠(쿠키)가 만료되면 아무것도 못 가져오고 ②너무 자주 부르면 차단될 수 있습니다.

5분이라는 간격은 이 둘 사이의 타협입니다. 더 짧게 하면 차단 위험이 커지고, 더 길게 하면 당일 취소 같은 급한 변경이 늦게 반영됩니다.

02언제 도는가

쉽게 말하면

자동으로 도는 게 3가지, 사람이 직접 누르는 게 1가지 있습니다. 네 가지 모두 결국 같은 작업을 하고, 차이는 “어느 범위를 확인하느냐”뿐입니다.

03전체 순서도

쉽게 말하면

한 번 실행되면 9단계가 순서대로 돕니다. 위쪽 4단계까지가 “예약을 우리 장부에 저장하는” 핵심이고, 그 아래는 저장된 예약을 바탕으로 이어서 하는 뒷일입니다.

◆ 표시는 “저장 확정” 지점입니다. 이 지점을 지나면 뒤에서 실패해도 앞의 결과는 남습니다. 점선 테두리는 “실패해도 앞 단계를 되돌리지 않는” 단계입니다.

04단계별 설명

  1. 1네이버에서 예약 목록 받아오기

    두 갈래로 물어봅니다(§01) — 최근 등록된 예약과 곧 체크인하는 예약. 둘을 합친 뒤 같은 예약이 양쪽에 들어 있으면 하나로 정리합니다. 로그인 쿠키가 만료됐으면 빈 목록을 받고 조용히 끝납니다.

    개발자용 — 코드와 진단

    real/reservation.py :: sync_reservations() — REGDATE 1일 + USEDATE 오늘~내일 2-leg fetch, bookingId 병합. from_date 지정 시 30일 청크 반복(USEDATE leg 생략). external_id 기준 재중복 제거는 naver_sync.py 상단.

    diag: naver_sync.enter · naver_sync.fetched · naver_api.fetch_page.{enter,exit}

  2. 2모자란 정보 채우기

    네이버가 주는 건 상품 번호와 “몇 건”이라는 숫자뿐입니다. 우리 장부에서 그 상품이 무엇인지 찾아 방 이름 · 실제 인원 · 남녀 구성 · 도미토리인지 여부를 채웁니다.

    여기서 가장 헷갈리는 게 “몇 건”이라는 숫자의 의미가 상품마다 다르다는 점입니다. 도미토리면 사람 수, 일반 객실이면 방 개수를 뜻합니다. 자세한 건 §05.

    개발자용 — enrichment 규칙

    NaverBizItem(상품명·섹션힌트·기본 파티타입·기본 정원) + RoomBizItemLink→Room (도미토리 여부·base_capacity) 을 맵으로 만들어 res_data에 주입. 매핑 없는 상품은 _has_room_link=False 로 표시되어 분할·자동배정 대상에서 제외됩니다.

  3. 3방 여러 개 예약 나누기

    일반 객실을 2개 이상 잡은 새 예약을 여러 건으로 쪼갭니다. 우리 시스템은 “예약 1건 = 방 1개” 구조라 나누지 않으면 방을 두 개 배정할 방법이 없습니다. 자세한 건 §06.

  4. 4우리 장부에 저장 ◆ 저장 확정

    이미 있는 예약이면 바뀐 것만 고치고, 없으면 새로 만듭니다. 이때 운영자가 손으로 고쳐둔 값은 건드리지 않습니다(§07). 날짜가 바뀌었으면 방 배정을 옮기고, 인원이 바뀌었으면 정원 검사를 다시 하고, 취소로 바뀌었으면 연박 묶음에서 빼는 뒷정리가 자동으로 따라붙습니다.

    개발자용 — 업서트와 라이프사이클 훅

    external_id/naver_booking_id 일괄 조회 1회 → _create_reservation() / _update_reservation(). 수정 경로는 ReservationMutator.apply_changes(ChangeSource.NAVER, …) 를 통과해 pin 필드를 guarded skip 합니다.

    후처리 훅: on_dates_changed() · on_constraints_changed() · on_status_cancelled(). 루프 안에서는 DB flush 금지 — 경보 후보는 파이썬 리스트에만 모읍니다.

    수집 결과: new_reservation_ids(신규) · date_changed_ids(날짜 변경) → 이후 단계의 작업 대상

  5. 5나뉜 예약끼리 어긋났는지 검사 ◆ 저장 확정

    3단계에서 나눈 예약들은 네이버 쪽에 짝이 없습니다. 그래서 네이버에서 일부만 취소되면 우리 쪽 여러 건 중 어느 걸 지워야 할지 알 수 없습니다. 이 단계는 그런 어긋남을 감지해 알림만 띄웁니다 — 자동으로 지우지 않는 이유는 잘못 지우면 되돌릴 수 없기 때문입니다.

    개발자용 — 4종 경보와 모드

    services/split_group_guard.py — 취소 고아(alert_cancel_orphan), 개수 drift(alert_bc_drift), 부활 고아(alert_reactivated_orphan), 미분할 다객실(alert_unsplit_multi). SPLIT_CANCEL_MODE=alert(기본) / auto(비보호 sibling 자동 취소). 전체 try/except 로 격리 — 실패해도 이후 단계는 정상 진행.

  6. 6연박 손님 묶기

    같은 이름·전화번호로 날짜가 이어지는 예약들을 하나의 묶음으로 연결합니다. 묶인 안에서 같은 방인데 침대 순서가 다르면 통일합니다. 청소팀 화면과 연박 안내 문자가 이 결과를 씁니다.

    개발자용

    consecutive_stay.detect_and_link_consecutive_stays() → _align_bed_orders_for_groups(). 하루 4회(9~12시) 별도 잡으로도 재확인.

  7. 7객실 자동 배정

    새로 들어오거나 날짜가 바뀐 예약이 걸친 날짜들만 골라 배정을 돌립니다. 여기에 운영 규칙이 하나 있습니다 — 오후 3시 컷오프. 3시 이전이면 오늘 날짜도 자동 배정하지만, 3시 이후에 들어온 당일 체크인 예약은 자동 배정하지 않고 운영자에게 맡깁니다. 아침 대조(09:55)는 항상 오늘을 포함합니다.

    개발자용

    SAME_DAY_AUTO_CUTOFF_HOUR = 15 · auto_assign_rooms(db, date, created_by="sync"|"reconcile"). diag naver_sync.phase5 에 대상 날짜·컷오프 적용 여부 기록.

  8. 8보낼 문자 목록 다시 계산 ◆ 저장 확정

    방 배정이 끝난 다음에 계산합니다. 순서가 중요한 이유는, “○○동 손님에게만” 같은 조건이 붙은 문자는 방이 정해지기 전에는 대상을 고를 수 없기 때문입니다.

    여기서 이미 보낸 문자와 사람이 직접 손댄 항목은 지우지 않습니다. 기본 안내 외에 인원 초과 안내 · 무료 업그레이드 약속/후기 안내도 함께 다시 계산됩니다.

    개발자용 — 칩 재계산과 보호 규칙

    reconcile_chips_for_reservation() + reconcile_surcharge_batch() + reconcile_room_upgrade_promise_batch() / _review_batch(). 보호: assigned_by ∈ {manual, excluded} 이거나 sent_at IS NOT NULL 인 칩은 삭제 대상 아님.

    안전장치: 스케줄 조회 시 tenant_id 명시 필터를 한 번 더 겁니다 — 과거 bypass 유출로 다른 테넌트 스케줄이 딸려온 사고 이력이 있습니다.

  9. 9즉시 안내 문자 발송

    새 예약 중 “예약 직후 보내기” 조건에 맞는 건에 문자를 바로 보냅니다. 완전히 분리된 상태로 실행되어 어떤 오류가 나도 위로 번지지 않습니다 — 문자 발송 실패가 예약 저장을 되돌리면 안 되기 때문입니다.

    개발자용

    event_sms_hook.schedule_event_sms_hook(ids, tenant_id) — 별도 DB 세션, fire-and-forget, 예외 절대 전파 안 함.

05네이버가 주는 것 / 우리가 채우는 것

쉽게 말하면

네이버는 “상품 번호 A, 1건, 김지현, 010-…” 정도만 줍니다. 그게 몇 인실인지, 몇 명이 오는지, 도미토리인지는 우리 장부의 상품 등록 정보를 보고 우리가 채웁니다.

그래서 상품 등록이 안 돼 있으면 시스템은 그 예약을 어떻게 다뤄야 할지 모릅니다. 이게 이 기능에서 사고가 가장 잘 나는 지점입니다.

같은 “1건”이 상품마다 다른 뜻

상품 종류“건수”의 뜻인원은 어떻게 정하나남녀 인원 갱신
도미토리사람 수건수 = 인원매번 다시 계산
액티비티
(투어·체험)		신청 인원건수 = 인원매번 다시 계산
일반 객실방 개수예약 시 고른 인원 → 없으면 방 기준 인원처음 한 번만
제2 사업장사람 수건수 = 인원요청서 글에서 “남 2 여 1” 같은 표기를 읽어냄

상품이 등록 안 돼 있으면 어떻게 되나

시스템은 아무것도 하지 않습니다. 나누지도 않고 자동 배정도 하지 않고, 네이버가 준 값 그대로 둡니다. 틀린 값을 조용히 만들어내는 것보다 낫다고 판단한 설계입니다.

증상: 새로 팔기 시작한 상품의 예약이 들어오긴 하는데 방이 배정되지 않는다 → 확인: 객실 설정 탭에서 그 상품이 방과 연결돼 있는지 봅니다.

06“방 3개 예약” 문제

쉽게 말하면

손님이 네이버에서 방 3개를 한 번에 예약하면 네이버는 이걸 예약 1건으로 보냅니다. 그런데 우리 시스템은 “예약 1건 = 방 1개” 구조라 그대로 저장하면 방 3개를 배정할 방법이 없습니다.

그래서 저장할 때 대표 예약 1건 + 딸린 예약 2건으로 나눕니다. 인원과 금액도 나눠 담되 총합은 원래와 같게 맞춥니다.

나누지 않는 경우 4가지

이런 경우엔 안 나눔이유
1건짜리 예약나눌 게 없음
도미토리거기서 “3”은 방 3개가 아니라 사람 3명이라 나누면 안 됨
상품 등록이 안 된 것차량 투어 같은 비숙박 상품일 수 있음 — 방처럼 쪼개면 운영 사고
이미 저장돼 있는 예약처음 들어올 때 이미 나눴음 — 또 나누면 중복

알아둬야 할 한계

딸린 예약은 네이버 쪽에 대응하는 짝이 없습니다. 그래서 손님이 네이버에서 3개 중 1개만 취소해도 시스템은 우리 쪽 어느 건을 지워야 할지 알 수 없습니다. 이럴 때 자동으로 지우지 않고 활동 로그에 알림만 남깁니다 — 처리는 운영자 판단입니다.

07사람이 고친 값은 건드리지 않는다

쉽게 말하면

5분마다 자동으로 도는 기능의 가장 큰 위험은 운영자가 방금 손으로 고친 걸 되돌려 놓는 것입니다. 그래서 사람이 한 번 손댄 자리에는 “건드리지 마” 스티커가 붙고, 네이버 값이 그 자리를 덮지 못합니다.

보호되는 것어떤 상황에서어떻게 동작하나
손님 이름 · 연락처
요청사항		 운영자가 직접 수정했을 때 네이버가 다른 값을 보내와도 무시하고 수정한 값 유지
퇴실 날짜 운영자가 연박을 늘려줬을 때 네이버가 더 짧은 날짜를 보내면 무시. 나중에 네이버가 따라잡으면 스티커 자동 제거
취소 상태 운영자가 시스템에서 직접 취소했을 때 네이버가 “확정”이라고 보내도 되살아나지 않음
남녀 인원 운영자가 직접 입력했을 때 자동 재계산 자체를 하지 않음
나뉜 예약의 인원·금액 방 여러 개 예약을 나눈 뒤 네이버 원본으로 덮으면 나뉜 것들의 합이 어긋나므로 고정

애매하면 고치지 않고 사람을 부릅니다

스티커가 붙어 있는데 네이버 상태와 우리 상태가 서로 다르면, 시스템은 자동으로 맞추지 않고 경고만 남깁니다. 반대로 양쪽이 이미 같은 상태라면 그 스티커는 과거의 잔재이므로 스스로 떼어냅니다. 확실할 때만 고치고 애매하면 사람에게 넘기는 원칙입니다.

09문제 생겼을 때 확인 순서

쉽게 말하면

“예약이 안 들어와요”라는 말이 나올 때, 위에서부터 순서대로 확인하면 대부분 여기서 원인이 나옵니다.

운영자용 점검 순서

  1. 로그인 쿠키가 살아 있나? — 연동 설정 탭에서 상태를 봅니다. 만료됐으면 예약을 하나도 못 가져오므로 모든 증상이 여기서 시작됩니다. 가장 흔한 원인입니다.
  2. 자동 확인이 실제로 돌고 있나? — 활동 로그에 동기화 기록이 계속 쌓이고 있는지 봅니다. 프로그램 재시작 후 자동 작업이 안 붙었으면 여기서 드러납니다.
  3. 가져오기는 되는데 저장이 안 되나? — 네이버에서 받아온 건수는 있는데 새 예약이 안 생긴다면 상품 정보 문제일 가능성이 큽니다.
  4. 특정 상품만 안 들어오나? — 객실 설정 탭에서 그 상품이 방과 연결돼 있는지 확인합니다(§05).
  5. 예약은 있는데 방만 비어 있나? — 오후 3시 이후 들어온 당일 예약이면 정상 동작입니다(§04 7단계). 아니면 배정 실패이므로 수동 배정하거나 다음 날 10:01 작업을 기다립니다.
  6. 방은 있는데 문자만 안 나가나? — 템플릿 설정에서 그 문자의 발송 조건(건물·객실·기타 조건)을 확인합니다.

11용어 사전

동기화
네이버 장부와 우리 장부를 대조해서 맞추는 일. 네이버가 먼저 알려주지 않아 우리가 5분마다 물어봅니다.
대조 (대사)
놓친 게 없는지 처음부터 다시 확인하는 일. 매일 오전 9:55에 오늘·내일 체크인 예약을 통째로 다시 봅니다.
쿠키
네이버에 로그인한 상태를 증명하는 열쇠. 만료되면 예약을 하나도 못 가져옵니다. 연동 설정 탭에서 갱신합니다.
저장 확정
여기까지 한 작업을 장부에 확실히 기록하는 지점(순서도의 ◆). 지나고 나면 뒤에서 실패해도 되돌아가지 않습니다.
문자 예약표
“이 손님에게 · 이 문자를 · 이 날 보낸다”를 적어둔 한 줄. 예약이 바뀌면 다시 계산되지만, 이미 보낸 줄과 사람이 손댄 줄은 지우지 않습니다.
대표 예약 / 딸린 예약
방 여러 개를 한 번에 예약한 건을 나눌 때, 네이버 예약번호를 갖는 쪽이 대표, 나머지가 딸린 예약. 네이버의 변경은 대표에만 전달됩니다.
건드리지 마 스티커 (pin)

오후 3시 컷오프
3시 이후에 들어온 당일 체크인 예약은 자동 배정하지 않고 운영자에게 맡기는 규칙. 체크인이 임박해 사람 판단이 필요하기 때문입니다.
제2 사업장 (언스테이블)

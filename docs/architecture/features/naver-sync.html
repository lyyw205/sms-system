네이버 예약 동기화

네이버 스마트플레이스의 비공개 예약 API를 5분마다 폴링해 로컬 DB와 맞추고, 그 결과로 연박 감지 · 객실 자동배정 · SMS 칩 생성 · 즉시 발송까지 연쇄로 태우는 파이프라인입니다. 시스템에서 바깥세상이 들어오는 유일한 입구입니다.

00한눈에

네이버는 예약 웹훅을 주지 않습니다. 그래서 이 기능은 “받는” 기능이 아니라 주기적으로 긁어와 차이를 맞추는 대사(對査) 기능입니다. 예약이 새로 생겼는지, 날짜가 바뀌었는지, 취소됐는지를 매번 전체 비교로 판정하고, 바뀐 것이 있으면 그 뒤에 붙은 배정·SMS 체계를 함께 재계산합니다.

01진입점 — 같은 함수, 4가지 호출

네 경로 모두 최종적으로 sync_naver_to_db()를 부릅니다. 차이는 어떤 날짜 필터로 긁어오는가와 당일 예약을 자동배정에 포함하는가 두 가지뿐입니다.

02파이프라인

03단계 상세

  1. P1조회 · 중복 제거real/reservation.py :: sync_reservations()

    기본 모드는 두 번 긁습니다. ①등록일(REGDATE) 최근 1일 — 방금 새로 잡히거나 취소된 예약을 잡고, ②체크인일(USEDATE) 오늘~내일 — 몇 주 전에 예약해 두고 체크인 당일 취소한 손님을 잡습니다. USEDATE 쪽이 없으면 그런 취소는 다음 09:55 대사까지 최대 하루 동안 보이지 않습니다. 두 결과는 bookingId로 병합되고, 월 단위 청크가 겹칠 수 있어 external_id 기준으로 한 번 더 중복 제거됩니다.

    실패 시
    쿠키 없음 → 빈 배열 반환 후 조용히 종료. HTTP 오류 → 이 테넌트만 롤백, 다음 테넌트 계속
    diag
    naver_sync.enter · naver_sync.fetched · naver_api.fetch_page.{enter,exit}
  2. P2정규화 (enrichment)naver_sync.py :: sync_naver_to_db()

    네이버가 주는 건 상품 ID와 예약 건수뿐입니다. 여기서 DB의 NaverBizItem · RoomBizItemLink를 조회해 상품명 · 실제 인원 · 도미토리 여부 · 기준인원 · 섹션(파티/객실/액티비티) · 기본 파티타입을 채웁니다. 같은 bookingCount 값이 상품 종류에 따라 인원수가 되기도 하고 객실 수가 되기도 하는 것이 이 단계의 핵심 분기입니다(§05).

    가드
    RoomBizItemLink 매핑이 없는 상품(차량투어 등)은 _has_room_link=False로 표시돼 분할·자동배정 대상에서 제외
  3. P2.5다객실 분할_split_multi_room_reservations()

    일반실을 2개 이상 잡은 신규 예약을 primary 1건 + sibling N−1건으로 쪼갭니다. 상세는 §06.

  4. P2업서트 → commit ①_create_reservation() / _update_reservation()

    external_id/naver_booking_id로 기존 예약을 일괄 조회한 뒤(쿼리 1회) 신규는 INSERT, 기존은 필드 비교 갱신입니다. 갱신 경로는 운영자 수동 편집을 덮지 않도록 ReservationMutator를 통과하며(§07), 날짜가 바뀌었으면 on_dates_changed(), 인원·성별이 바뀌었으면 on_constraints_changed(), 취소로 바뀌었으면 on_status_cancelled() 라이프사이클 훅이 걸립니다.

    수집
    new_reservation_ids(신규) · date_changed_ids(날짜 변경) — 뒤 단계의 작업 대상
    주의
    루프 안에서는 DB 쓰기/flush를 하지 않습니다. 경보 후보는 파이썬 리스트에만 모아두고 commit 이후에 처리 — 세션 오염 방지
  5. P2.8분할그룹 정합 가드 → commit ②services/split_group_guard.py

    분할된 예약은 네이버 쪽 변경이 primary 에만 반영됩니다. 그래서 네 가지 어긋남을 감지해 경보합니다 — primary 취소인데 sibling 이 남은 취소 고아, 네이버 객실 수와 그룹 크기가 다른 drift, 취소됐다 되살아난 부활 고아, 분할 안 된 예약의 객실 수가 1→N 으로 늘어난 미분할 다객실.

    모드
    SPLIT_CANCEL_MODE=alert(기본) 경보만 / auto 보호되지 않은 sibling 자동 취소
    격리
    전체 try/except. 실패해도 P4 이후는 정상 진행 — 5분 뒤 재시도
  6. P4연박 감지services/consecutive_stay.py

    같은 이름+전화로 날짜가 이어지는 예약들을 stay_group으로 묶고, 묶인 그룹 안에서 같은 방인데 침대 순서가 다르면 통일합니다(_align_bed_orders_for_groups). 청소·연박 안내 화면이 이 결과를 씁니다.

  7. P5객실 자동배정services/room_auto_assign.py

    신규 예약과 날짜가 바뀐 예약이 걸친 날짜들만 골라 자동배정을 돌립니다. 여기에 운영 규칙이 하나 있습니다 — 15시(KST) 컷오프: 15시 이전이면 오늘 날짜도 자동배정하지만, 15시 이후에 들어온 당일 예약은 체크인이 임박했으므로 자동배정하지 않고 운영자 수동 배정에 맡깁니다. 09:55 대사 경로는 항상 오늘을 포함합니다.

    diag
    naver_sync.phase5 — 대상 날짜 · 컷오프 적용 여부 기록
  8. P5.5SMS 칩 재계산 → commit ③chip_reconciler · surcharge · room_upgrade_*

    배정이 확정된 다음에 칩을 계산합니다. 순서가 중요합니다 — 건물/객실 필터가 걸린 스케줄은 RoomAssignment이 없으면 칩이 만들어지지 않기 때문입니다. 예전에는 P3와 P5.5 두 번 돌렸지만 지금은 배정 이후 1회로 통합돼 연산이 절반입니다. 표준 칩에 이어 초과요금 · 업그레이드 약속 · 업그레이드 후기 칩도 같은 대상 목록으로 재계산됩니다.

    안전
    테넌트 ID를 명시 필터로 한 번 더 검사. 과거에 bypass 유출로 다른 테넌트 스케줄이 딸려온 사고가 있었음
    보호
    assigned_by ∈ {manual, excluded} 이거나 sent_at이 있는 칩은 재계산이 지우지 않음
  9. P6이벤트 SMS 즉시 발송services/event_sms_hook.py

    신규 예약 중 활성 이벤트 스케줄(성별 조건 · 예약 후 경과시간 등)에 맞는 건에 즉시 안내 문자를 보냅니다. 별도 DB 세션을 쓰고 어떤 예외도 위로 던지지 않습니다 — 문자 발송 실패가 예약 동기화를 되돌리면 안 되기 때문입니다.

06다객실 분할

네이버는 “객실 3개”를 예약 한 건으로 보냅니다. 반면 우리 스키마는 RoomAssignment(reservation_id, date)에 유니크 제약이 있어 예약 1건 = 방 1개 = 날짜 1개 모델입니다. 그대로 저장하면 3개 방을 배정할 방법이 없습니다.

분할하지 않는 4가지 경우

스킵 조건이유
bookingCount ≤ 1나눌 것이 없음
도미토리 상품bookingCount 가 객실 수가 아니라 인원 수
RoomBizItemLink 매핑 없음정체 불명 상품(차량투어 등)을 객실처럼 쪼개면 운영 사고
이미 DB에 있는 예약첫 동기화 때 처리 완료 — 재분할 금지

분할 예약의 알려진 한계

sibling 은 네이버 쪽에 대응하는 행이 없습니다. 따라서 네이버에서 3개 중 1개만 취소해도 시스템은 어느 sibling 을 지워야 할지 알 수 없습니다. 이 때문에 자동 전파는 기본적으로 꺼져 있고(alert 모드), P2.8 가드가 “그룹이 어긋났다”는 경보만 띄웁니다. 처리는 운영자 판단입니다.

07보호 규칙 — 자동화가 사람을 덮지 않게

5분마다 도는 자동 동기화의 가장 큰 위험은 운영자가 방금 손으로 고친 값을 되돌려 놓는 것입니다. 그래서 “한번 사람이 만진 필드”에는 핀이 박히고, 네이버 값은 그 필드를 건드리지 못합니다.

핀보호 대상동작해제 조건
manually_edited_fields 이름 · 전화 · 방문자 정보 · 요청사항 ReservationMutator가 ChangeSource.NAVER 변경을 guarded → skip 운영자가 해당 필드를 되돌릴 때
check_out_pinned 퇴실일(연박 연장/축소) 들어온 값이 더 짧으면 무시. 네이버가 따라잡으면 핀 자동 해제 1박으로 완전 철회 또는 네이버가 같은 값으로 갱신
manually_edited_fields["status"] 운영자 수동 취소(소프트 취소) 네이버가 confirmed 를 보내도 부활 차단 PATCH 로 confirmed 복원 시 · 양측 합의 상태면 self-heal
gender_manual 남/여 인원 True 면 자동 재계산 자체를 하지 않음 운영자 해제
split_group_id 보유 분할 예약의 인원·금액·객실수 네이버 원본으로 덮으면 sibling 합계가 어긋나므로 동결 없음(설계상 유지) — 상품 매핑이 풀려도 동결 유지

self-heal 과 경보의 구분

status 핀이 있는데 예약이 CONFIRMED 이고 네이버도 confirmed 라면, 그 핀은 과거의 잔재입니다 — 자동으로 핀을 지우고 naver_sync.status_pin_self_healed를 남깁니다. 반면 핀이 있는데 양측 상태가 서로 다르면 자동 보정하지 않고 naver_sync.status_pin_invariant_violation 경보만 냅니다. 확실할 때만 고치고, 애매하면 사람을 부르는 원칙입니다.

“예약이 안 들어와요” 점검 순서

  1. 쿠키 — 연동 설정 탭에서 상태 확인. 만료면 조회 결과가 통째로 비어 모든 증상이 여기서 시작됩니다.
  2. 잡 상태 — GET /api/scheduler/jobs로 sync_naver_reservations의 다음 실행 시각 확인. 프로세스 재시작 후 등록 실패면 여기서 드러납니다.
  3. 조회 자체 — naver_sync.fetched의 raw_count. 0이면 API/쿠키 문제, 0이 아닌데 저장이 없으면 매칭·정규화 문제.
  4. 상품 매핑 — 특정 상품만 안 들어오면 NaverBizItem·RoomBizItemLink 등록 여부(§05 주의 박스).
  5. 배정만 비었나 — 예약은 있는데 방이 없으면 15시 컷오프이거나 P5 실패. 10:01 잡 또는 수동 배정으로 회복.
  6. 칩만 비었나 — 배정이 있는데 칩이 없으면 스케줄 필터 조건(건물/객실/컬럼 매칭) 확인.

아키텍처 맵 §03에서 이 기능은 1차 분리 대상(①)입니다. 이유와 경계는 다음과 같습니다.

구분분리 후 배치
워커로 나갈 것real/reservation.py (외부 호출) · P1 조회 · P2 정규화 · P2.5 분할 판정
코어에 남을 것P2 업서트 · P2.8 가드 · P4 연박 · P5 배정 · P5.5 칩 — 모두 Stay Core 트랜잭션
